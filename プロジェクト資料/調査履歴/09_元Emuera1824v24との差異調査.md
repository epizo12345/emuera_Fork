# 元Emuera（1824+v24）との差異調査

以前使っていたEmuera 1824+v24（GDI+描画）から、.NET版（Skia描画、本fork）へ移行したことで、同じERBでも挙動が変わる箇所を調べた記録。段階的に進める。

- 調査開始: 2026-10-28
- 現在の段階: 第1段階（描画まわり）、第2段階（関数・演算子・命令・セーブ形式・設定）、第3段階（元EXEと現行EXEの実行比較）完了。

## 比較対象

| 区分 | 場所 |
|---|---|
| 元Emueraのソース | `E:\GAME-2\Emuera1824+v24\Emuera1824+v24\src1824+v24\src1824\Emuera` |
| 元EmueraのEXEで起動できる実ゲーム | `E:\GAME-2\eraMegaten_6954\ShinEraTensei1.0用私家版パッチ纏め_Rev168\00_データ本体`（`Emuera1824+v24.exe`） |
| 本forkで使っているゲーム | `E:\GAME-2\eramegaten_p-master\eramegaten_p-master` |
| 本forkのソース | このリポジトリ（比較時点のHEAD `8332563`） |

元EmueraのEXEで起動できるゲームは、本forkで使うゲームとはバリアントが違う。現行ゲームは元Emueraでは起動しない想定のため、実画面比較はこの参考用ゲームで行うか、GDI+を直接呼ぶ試験で行う。

## 方法

- 組み込み関数・命令の登録一覧（`Creator.cs`の関数名、`BuiltInFunctionCode`の命令名）を突き合わせた。
- 同名関数の実装を、元と現行で並べて読んだ。
- 怪しい箇所は、一時プロジェクトで本forkの`GraphicsImage`と、元と同じ設定のGDI+（System.Drawing）を同じ入力で実行し、画素値を比べた。

## 第1段階: 描画まわり

### 関数・命令の有無

元Emueraにある組み込み関数（163個）・命令（267個）は、すべて現行にも存在する。削除されたものはない。現行で増えたのは`GDRAWTEXT`、`G_POLYGON_*`、`DICT_*`、`SQL_*`、`HASH_XXH*`、`GETCSVNOBY*`、`EXISTFUNCTION`など。

### 修正済み

| 項目 | 内容 | 対応 |
|---|---|---|
| カラーマトリクスの平行移動 | `GDRAWG`／`GDRAWCIMG`／`GDRAWSPRITE`で5行目（色に足す値）が無視され、色が明るくなっていた | `bf6e2d6`で修正、配布EXE更新済み |

### 確認できた差異（未修正）

いずれも実行比較で確認した。

#### 1. `GDRAWG`の拡大縮小が補間なしになっている

- 元: `GCREATE`／`GCREATEFROMFILE`したGに`InterpolationMode.Bicubic`＋`PixelOffsetMode.Half`を設定しており、`GDRAWG`・`GDRAWSPRITE`の拡大縮小はbicubic。
- 現行: `GDRAWG`は`AImage.Draw`が`SKSamplingOptions.Default`（最近傍）固定（`UI/Game/Image/AImage.cs:43`）。設定の画像補間を無視する。
- `GDRAWSPRITE`・`PRINT_IMG`・HTMLの`<img>`は設定`ImageSamplingOption`（既定Linear、ゲームのsetting.jsonも1=Linear）に従う。元はGへの描画がbicubic、画面への描画はGDI+既定（Bilinear）。
- 実測（黒白2pxを8pxへ拡大したR値）:
  - 元: `0 0 23 99 185 245 254 254`
  - 現行: `0 0 0 0 255 255 255 255`
- 影響: `GDRAWG`で拡大縮小した画像がギザギザになる。等倍描画には影響しない。
- 修正案: `GDrawG`でも`JSONConfig.SamplingOptions`を渡す（数行）。元と完全一致させるならCubicだが、他の描画経路と揃えて設定に従わせるのが自然。
- **修正（ブランチ`epizo/描画差異修正`、DRAW-08）**: 設定の画像補間に従うようにした（カラーマトリクス付きも同じ）。元と同じbicubicにしたい場合は設定でCubicを選ぶ。

#### 2. ごく低いアルファの色を書くと、RGBが失われる

- 元: `Format32bppArgb`（アルファを掛け込まない形式）で保存。`GSETCOLOR`した値がそのまま`GGETCOLOR`で返る。
- 現行: `new SKBitmap(w, h)`の既定はpremultiplied（アルファを掛け込んだ形式）。アルファが0に近いほどRGBの精度が落ち、0では完全に失われる。
- 実測（`GSETCOLOR`→`GGETCOLOR`、ARGB）:

| 書いた値 | 元 | 現行 |
|---|---|---|
| `00FF0000` | `00FF0000` | `00000000` |
| `01FF8040` | `01FF8040` | `01FFFF00` |
| `80FF8040` | `80FF8040` | `80FF8040` |
| `7F123456` | `7F123456` | `7F123456` |
| `FF123456` | `FF123456` | `FF123456` |

- 影響: 透明画素に色情報を持たせる処理、`GGETCOLOR`／`SPRITEGETCOLOR`の値比較、`GDRAWGWITHMASK`などの画素合成で結果が変わり得る。中間のアルファ（0x7F〜0x80）は今回の値では一致した。
- 修正案: G用Bitmapを`SKAlphaType.Unpremul`で作る。ただし描画・合成・PNG保存・GPU経路すべてに関わるため影響範囲が広い。採用前に描画全般の回帰確認が必要。
- **見送り（2026-10-28決定）**: 現行ゲームのERBに`GSETCOLOR`／`GGETCOLOR`／`SPRITEGETCOLOR`／`GBITMAPTOINT`／`GBYTEARRAYTOBITMAP`／`GDRAWGWITHMASK`の使用がなく実害がない一方、直すには描画全体に関わる保存形式の変更が必要なため。

#### 3. ブラシ未設定の`GFILLRECTANGLE`が黒になる

- 元: `GSETBRUSH`していなければ`Config.BackColor`（背景色）で塗る。
- 現行: 既定の`SKPaint`（`FF000000`、黒）で塗る（`UI/Game/Image/GraphicsImage.cs`の`GFillRectangle`）。
- 影響: `GSETBRUSH`せずに`GFILLRECTANGLE`している箇所だけ。背景色が黒のゲームでは見た目は同じ。
- 修正案: 既定の色を`Config.BackColor`にする（数行）。
- **修正（ブランチ`epizo/描画差異修正`、DRAW-07）**: 元と同じく背景色で塗るようにした。

### 差異なし・影響なし（コードで確認）

- HTMLの`<img>`の`height`／`width`／`ypos`: 元と同じく「フォントサイズの%」。現行では呼び出し側（`HtmlManager.ParseSizeValue`）でpxへ変換してから渡す。`px`指定は現行で追加された機能。
- 画像・図形のX位置補正: 元は画像・図形だけ`max(2, FontSize/6)`px右へずらし、現行は行全体を一律3pxずらす。ゲーム設定のフォントサイズ18では元も3pxで同じ。フォントサイズ24以上では元の方が大きくずれる。
- `GSAVE`／`GLOAD`: どちらもPNG。現行はWINAPI描画モードでエラーにするが、現行はWINAPIモード自体をTEXTRENDERERへ置き換えるため実害なし。
- `GSETPEN`: 元は引数型の定義が2個なのに3番目を読んでおり、正しく呼べなかった。現行は3引数で動く（現行の方が正しい）。
- `ConsoleImagePart`の`XsubPixel`: 現行は幅指定時の計算が元と異なるが、値は受け渡されるだけで位置計算に使われていないため影響なし。

- `SPRITEANIME*` → 未調査
- `CBG*`の描画順・ボタン当たり判定 → 未調査

## 第2段階: 描画以外

### 方法

- 組み込み関数クラス（元122個）、演算子クラス（39個）、命令クラス（82個）を、書式差（`Int64`→`long`、`IOperandTerm[]`→`List<AExpression>`、括弧・空白、メッセージ文字列）を正規化して類似度で並べ、差の大きいものを読んだ。比較スクリプトは一時フォルダで実行し、リポジトリには置いていない。
- 文字数計算（`LangManager`）、セーブの読み書き（`EraBinaryDataWriter`／`Reader`）、設定項目（`ConfigCode`）と初期値（`ConfigData`）はファイル単位で差分を取った。
- `CHECKFONT`は一時プロジェクトでGDI+とSkiaのフォント一覧を実際に比べた。

### 確認できた差異

#### 4. `BEGIN`のキーワードが大文字小文字を区別するようになった

- 元: 設定「大文字小文字の違いを無視する」がYESなら、`BEGIN shop`のような小文字も通る（`keyword.ToUpper()`）。
- 現行: 上流commit `473911c`（不要なToUpperを排除）でこの処理が消え、`Process.State.SetBegin`は大文字の`SHOP`などとしか一致しない。小文字だと「BEGINのキーワード"shop"は未定義です」エラー。
- 同じcommitで`CALLFORM`／`TRYCALLFORM`／`CALLF`／`CALLEVENT`／`LOCAL@関数名`の大文字化も消えたが、これらは関数辞書が設定に応じて大文字小文字を無視する比較（`Config.StrComper`）になっているため影響なし。影響が出るのは`BEGIN`だけ。
- 現行ゲーム（eramegaten_p）のERBには大文字以外の`BEGIN`はなく、実害なし。

#### 5. `CHECKFONT`で、太さ違いのフォント名の扱いが変わった

- 元: GDI+の`InstalledFontCollection`。`Arial Black`、`BIZ UD明朝 Medium`、`Calibri Light`のような太さ違いを別のフォント名として返す。
- 現行: Skiaのフォント一覧（＋外部フォント）。太さ違いは元の名前（`BIZ UD明朝`など）にまとめられる。
- 実測（この環境）: GDI+ 254件、Skia 169件。GDI+だけにある名前92件（多くは`Light`／`SemiBold`／`Medium`／`Condensed`付き）、Skiaだけにある名前7件（`BIZ UD明朝`、`BIZ UDP明朝`、`Franklin Gothic`など）。
- `ＭＳ ゴシック`、`ＭＳ 明朝`、`メイリオ`、`游ゴシック`、`BIZ UDゴシック`など日本語名の通常フォントは、元・現行とも1。英語名（`MS Gothic`など）は元・現行とも0。
- 影響: 太さ違いの名前を`CHECKFONT`や`GSETFONT`／`SETFONT`で使う場合だけ。`GSETFONT`／`SETFONT`側でその名前が使えるかは未確認。

#### 6. `TOINT`で桁あふれする文字列が0を返すようになった

- 元: `TOINT("99999999999999999999")`のように64bit整数に入らない数字は、読み取り時の例外でエラーになる（コードからの推定）。
- 現行: 例外を捕まえて0を返す。
- 影響: 桁あふれする文字列を`TOINT`している場合だけ。

#### 7. `RAND`の最大値と最小値の差が64bitを超えるとエラーになった

- 元: 差の計算が桁あふれし、おかしな範囲で乱数を返す。
- 現行: エラー（「RANDの最大値と最小値の差が64ビット符号付き整数の最大値を超えています」）。極端な値を渡したときだけで、通常は影響なし。

### 差異なし・影響なし

- 関数クラス: `POWER`、時刻系（`GETTIME`など、計測版だけの分岐を除く）、`STRCOUNT`、`UNICODE`、`TOUPPER`／`TOLOWER`／`TOHALF`／`TOFULL`、`GETCONFIG`、`LOADTEXT`／`SAVETEXT`、`GETBIT`、`EXISTCSV`、`GETKEY`系、`GETBGCOLOR`などは、書式・メッセージ以外同じ。
  - `POWER`は元がdouble経由、現行は整数で正確に計算する。2^53を超える結果の下位桁だけ現行の方が正確になる。0の負の累乗・範囲外はどちらもエラー。
  - `TOUPPER`／`TOLOWER`は現行がInvariantCulture。日本語・英語では結果は同じ。
- 演算子: 全39種が実質同じ。単項マイナスで`long`最小値のとき、元は式を2回評価していたのが1回になった（現行の方が正しい）。0除算はどちらもエラー。文字列比較の大小は同じ設定（`SCExpression`）を使う。
- 命令: 82種すべて現行に存在。差があったのは`IF`（定数条件の高速化）、`REPEAT`／`BREAK`／`CONTINUE`（内部の型の整理）、`VARSET`（一時領域の再利用）、`PRINT`（`N`付きの派生命令を追加）、`HTML_PRINT`（行末を続ける第2引数を追加）で、既存の書き方の動作は同じ。
- 乱数: 設定`UseNewRandom`がfalse（現行ゲームのsetting.jsonもfalse）なら、元と同じメルセンヌ・ツイスタ。trueにすると別の乱数になり、`RANDOMIZE`／`DUMPRAND`／`INITRAND`は警告を出して無効になる。
- 文字数計算（`STRLENS`、`SUBSTRING`など）: 言語設定が日本語（コードページ932）なら元と同じ。現行は日本語以外の設定のときだけ、設定の文字コードで表せない文字をCP932で数える。
- セーブ・ロード: 先頭識別子・バージョン（1808）・データ型の書き方は同じ。現行の変更は書き出しの高速化と、全0配列の読み捨て・遅延確保などで、保存されるバイト列は同じ（本forkの回帰試験でバイト一致を確認済みとされている）。
- 設定（`emuera.config`）: 項目95個・初期値はすべて同じ。現行で`UseDarkMode`（既定true）が増えただけ。現行は描画モードWINAPIを受け付けず、TEXTRENDERERに置き換える。

### 3-2. 文字描画（スクリーンショット比較）

英数字・かな・漢字・記号・罫線、`PRINTC`／`PRINTLC`、`SETCOLOR`、`SETFONT`（ＭＳ 明朝）、`FONTBOLD`、`FONTITALIC`、書式付き表示、`ALIGNMENT RIGHT`／`CENTER`、`DRAWLINE`、`CUSTOMDRAWLINE`、長い行の折り返し、`HTML_PRINT`（`<font color>`、`<b>`、`<nonbutton>`）を表示し、同じウィンドウサイズで撮影して画素比較した。

- 通常の文字（明朝・色付き・揃え・折り返し・罫線・HTMLの色を含む）は、位置・形とも**画素単位で完全一致**。
- 違いは3行だけ（差のある画素は全体で2206）:
  - **差異8. 太字**（`FONTBOLD`、HTMLの`<b>`）: 位置・幅は同じだが、現行の方が線がやや細い。
  - **差異9. 斜体**（`FONTITALIC`）: 位置・幅は同じだが、現行は線がにじんで太めに見える。元は細くくっきり。
  - **差異8の追加確認（2026-10-28）**: ＭＳ ゴシック18pxでGDIの`TextRenderer`とSkiaを描き比べると、現行の太字（太字の書体を要求する方式）は線の量がGDIの99.6%で、太さは同じだった。見た目の差は太らせる向きの違いによる形の差。擬似太字（`Embolden`）を足すと153〜178%と太りすぎるため、**直さない**。
  - **差異9の修正（ブランチ`epizo/描画差異修正`、DRAW-09）**: 斜体は書体を傾けて作るため、内蔵のドット絵ではなく輪郭から滑らかに描かれ、線の量がGDIの約129%になってにじんでいた。通常の文字をドット絵（アンチエイリアスなし）で描くフォントと大きさでは、斜体もアンチエイリアスなしで描くようにした（GDIの99.5%、見た目もほぼ同じ）。滑らかに描くフォント（メイリオなど）の斜体は従来どおり。判定はフォント・大きさ・設定ごとに1回、試し描きで行う。
- 行の高さ、折り返し位置、`PRINTC`の幅、右寄せ・中央寄せの位置はすべて同じ。

### 3-3. 実ゲームの読み込み（参考用ゲーム、全ERB解析）

参考用ゲーム（ShinEraTensei 1000.16）の`ERB`／`CSV`／`resources`を作業フォルダへ1回だけコピーし、コピー側の設定だけ「ロード時に引数を解析する:YES」「呼び出されなかった関数を無視する:NO」に変えて読み込んだ。

#### 差異10. UTF-16で保存されたERB・CSVを読めない（現行では起動不能になる）

- 参考用ゲームの`CSV\悪魔\41_魔人\Chara4114_母子合体悪魔人.csv`だけがUTF-16（BOM付き）。他は Shift-JIS か UTF-8（BOM付き）。
- 元: .NETの`StreamReader`がBOMを自動判定するため、UTF-16も正しく読める。
- 現行: `Preload.ReadFileLines`がUTF-8のBOMしか見ず、UTF-16をShift-JISとして読んで文字化けする。このCSVだけで警告Lv1が数十件出る。
- さらに、その警告を表示する`Process.getRawTextFormFilewithLine`が、ファイルをShift-JISで読み直して行番号の行を`First()`で取り出すため、行が見つからず`InvalidOperationException`で**初期化中に異常終了**する。
- 現行ゲーム（eramegaten_p）の`Data`配下はERB・ERH・CSV 11,376件中、UTF-8（BOM付き）11,375件・BOMなし1件で、UTF-16はなく実害なし。
- 修正案: (1) `Preload.ReadFileLines`でUTF-16 LE／BEのBOMも判定する。(2) `getRawTextFormFilewithLine`は行がなければ空文字を返す（`FirstOrDefault`）。どちらも数行。
- **対応しない（2026-10-28決定）**: ゲーム側はERB・CSVをUTF-8（BOM付き）で作る運用に統一されているため。

#### 構文解析の結果

上のCSVを作業用コピー内でだけUTF-8（BOM付き）に変換して再実行すると、現行EXEは最後まで読み込めた。

- 元EXE・現行EXEとも、同じ警告Lv2が同じ順で10件（ゲーム側の記述によるもの: Rename失敗1件、未定義の関数2件、半角の`V経験`などCSVに無い名前7件）。
- 違いは、現行がRename失敗のときに警告Lv1の行を1行多く出すことだけ。
- 全ERB解析の範囲では、構文解析の差は見つからなかった。
