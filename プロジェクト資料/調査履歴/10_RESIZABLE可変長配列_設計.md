# RESIZABLE 可変長配列 設計メモ

- 作成: 2026-10-28
- ブランチ: `epizo/可変長配列`（mainには入れない）
- 状態: 実装済み（ブランチのみ）。フィクスチャ6/6・既存回帰92/92・現行ゲーム起動Lv2警告0

## 目的

`#DIM`／`#DIMS`で宣言した1次元配列の長さを、実行中に変えられるようにする。

主な用途:

- `SPLIT`などの出力先として、分割数を見越した過剰な配列を確保しなくて済むようにする。はみ出しによる切り捨てもなくす。
- 随時要素が増える一覧を配列で持つ。代表例は現行ゲーム（eramegaten_p）の戦闘効果`C_BTL_EFFECT`／`C_BTL_EFFECT_PERMANENCE`／`C_BTL_EFFECT_CHARGE`（`#DIMS CHARADATA`、1キャラ最大80件程度）。現在は要素0に`/`区切りで連結し、`ADD_SPLIT`で追加、`REPLACE`で削除、`STRCOUNT`で件数、`AUTO_SPLIT`でn番目を取り出しているため、`TRYSKILL`で全件を見るとキャラごとにn²回ぶんの文字列処理が発生している。

処理頻度の高い箇所で使う前提のため、**読み書きの速度を落とす仕様は採用しない**。

## 仕様

### 宣言

```
#DIM RESIZABLE 名前, 初期サイズ
#DIMS RESIZABLE 名前, 初期サイズ
#DIMS CHARADATA RESIZABLE 名前, 初期サイズ
```

- 1次元のみ。初期サイズは0も可（空）。省略時は従来どおり1。
- 使える場所: グローバル、関数内（`DYNAMIC`／`STATIC`）、`CHARADATA`。
- 同時に指定できないもの: `CONST`、`REF`、`SAVEDATA`、`GLOBAL`（セーブ形式で長さを扱う方法を決めるまで対象外）、2次元以上。
- 初期値指定（`= 1,2,3`）は従来どおり可。

### 動きのルール: 伸びるのは自動、縮むのは明示したときだけ

| 操作 | 動き |
|---|---|
| 範囲外の要素への書き込み（`X:n = v`、`X:n += v`） | 長さn+1まで自動で伸びる。途中は0／空文字。上限1,000,000要素（`#DIM`の上限と同じ） |
| 範囲外の要素の読み取り | 従来どおりエラー |
| 負の添字 | 従来どおりエラー |
| `SPLIT`／`HTML_TAGSPLIT`の出力先 | 分割数が長さを超えるときは伸びる。縮めない（後ろは従来どおり前回の値が残る）。分割数は従来どおり個数の変数で受け取る |
| `FINDELEMENT`など読むだけの配列関数 | 今の長さを全長として、そのまま動く |
| `ARRAYREMOVE`など中身を動かす配列関数 | 従来どおり。長さは変えない |
| サイズ変更命令 | 伸ばすのも縮めるのも可。縮める唯一の手段 |
| `REF`の参照先、参照渡しの引数（`REF`引数） | エラー（古い配列を見続ける問題を防ぐ） |

- 削除は「`FINDELEMENT`で位置を探す → `ARRAYREMOVE`で詰める → サイズ変更命令で1減らす」。専用の削除・追加命令は作らない。
- 末尾への追加は「今の長さの位置へ書き込む」（自動で伸びる）。

### 追加した関数（命令の形でも書ける）

- `RESIZE 変数, 新しい長さ`（`RESIZE(変数, 長さ)`も可）… 長さを変える。伸びた部分は0／空文字。戻り値は新しい長さ。`RESIZABLE`でない変数を渡すと読み込み時エラー。
- `ARRAYSIZE(変数)` … 今の長さを返す。`RESIZABLE`でない1次元配列は宣言時のサイズを返す。
- 既存の`VARSIZE("変数名")`は、`RESIZABLE`の広域・関数内変数では今の長さ、`CHARADATA`では宣言時の初期サイズを返す（キャラを指定できないため）。

### CHARADATAの書き方

Emueraのキャラ変数は、添字が1つ（`C_LIST:0`）だと「`TARGET`の0番目の要素」になる（`CFLAG:0`と同じ規則）。キャラを指定するときは添字を2つ書く。

```
C_LIST:ARG:(ARRAYSIZE(C_LIST:ARG:0)) '= "効果"   ; 末尾に追加
LOCAL = FINDELEMENT(C_LIST:ARG:0, "効果", 0, ARRAYSIZE(C_LIST:ARG:0), 1)
RESIZE C_LIST:ARG:0, 0                             ; 空にする
```

`FINDELEMENT`／`SUMARRAY`／`MAXARRAY`／`INRANGEARRAY`／`VARSET`は、範囲（終了位置）を省略すると、そのキャラの今の長さを使う（`MATCH`・`STRJOIN`も同じ対応を入れたが、キャラ変数に対してはもともと`MATCH`が一致を数えず、`STRJOIN`はキャラ変数を受け付けない）。広域・関数内の`RESIZABLE`は、範囲省略時に常に今の長さが使われる。

## 実装方針

### 中身の持ち方

**長さを変えるたびに、ちょうどの長さの配列に作り直す**（`Array.Resize`）。

- 「配列の全長＝今の長さ」が常に成り立つので、`GetArray()`／`GetArrayChara()`で配列を取り出して`.Length`を使う既存の配列関数（約73か所）は書き換えずに動く。
- 追加のたびに全体をコピーするが、想定する要素数（数十〜数百）ではコピーはERBの1命令の手間より小さい。要素数1万を超える用途で1個ずつ追加すると遅くなる（約2乗）。その場合は、先に`RESIZE`でまとめて伸ばしてから書き込む。
- 大きめに確保して長さを別に持つ方式は、追加は速いが、既存の配列関数約73か所を「今の長さ」に合わせて直す必要があり、範囲外の読み取りも自前で検出する必要があるため採用しない。

### 既存の変数を遅くしない

- `RESIZABLE`用に専用のトークンクラスを6つ作る（整数・文字列 × グローバル／関数内STATIC・関数内DYNAMIC・CHARADATA）。既存の`StaticInt1DVariableToken`などには手を入れないので、既存の`#DIM`の読み書きの処理は変わらない。
- 読み取りは既存と同じ`array[i]`。範囲外は従来どおり.NETの例外→`CheckElement`でエラーメッセージ。
- 書き込みだけ「添字が長さ以上なら伸ばす」比較を1回追加する（`RESIZABLE`変数のみ）。

### 長さの扱い

- 既存のユーザー定義トークンは宣言時のサイズ`sizes`（`UserDefinedVariableData.Lengths`と同じ配列オブジェクトを共有）で範囲チェック・`GetLength`・`IsArrayRangeValid`を行う。`RESIZABLE`トークンはこれらを今の配列の長さで判定するように上書きする。`Lengths`は共有されているため書き換えない。
- 関数内`DYNAMIC`: 再帰に備えて配列をスタックに退避する既存の作りを踏襲する。呼び出しごとに初期サイズの配列から始める。既存の「使い終わった配列を1つ再利用する」最適化は、長さが初期サイズと同じ場合だけ使う。
- `CHARADATA`: キャラごとの配列（`CharacterData.UserDefCVarDataList[ArrayIndex]`）を差し替える。キャラ追加時は初期サイズで作る（既存どおり）。`COPYCHARA`などキャラ間コピーは、コピー先をコピー元と同じ長さの配列に作り直してからコピーする。

### 読み込み時の範囲確認

添字がすべて定数の変数参照は、読み込み時（`VariableTerm.Restructure`）に`CheckElement`で範囲確認される。`RESIZABLE`は長さが実行時に決まるため、`ARG`／`ARGS`と同様にこの確認を省き、実行時に確認する。

### 安全性の確認（2026-10-28）

- `GetArray()`／`GetArrayChara()`を使う箇所はすべて「引数を評価してから配列を取り出す」順になっており、取り出した後に同じ変数の長さが変わる経路はない（取り出した後に`GetIntValue(exm)`等を呼ぶ箇所を機械的に検索し、該当は`REF`後の別命令の誤検出1件のみ）。
- 配列そのものを保持し続けるのは`REF`（`Instraction.Child.cs`の`SetRef`）と参照渡しの引数（`Process.CalledFunction.cs`の`TransporterRef`）だけ。どちらも`RESIZABLE`変数ならエラーにする。
- このforkの高速化（`FixedVariableTerm`の再利用、`CDFLAG`の遅延確保など）が保持するのはトークンであり、配列ではない。

### 速度（ERBで100万回繰り返し、2回目の値、ms）

| 項目 | 固定長 | RESIZABLE |
|---|---|---|
| 読み取り（広域） | 31 | 33 |
| 書き込み（広域） | 40 | 34 |
| 読み取り（CHARADATA） | 38 | 34 |
| 書き込み（CHARADATA） | 38 | 35 |
| 先に長さを確保してから書き込み | — | 35 |
| 末尾への追加（80件のリストを作る） | 50（件数変数で管理） | 78（`ARRAYSIZE`で長さを取って追加） |
| 添字を指定して1個ずつ追加 | — | 70 |
| `ARRAYSIZE`の呼び出し | — | 34（空ループとの差 約22ns） |
| TRYSKILL型（効果20件を番号順に全部見る×5000回） | 72（`/`区切り＋`STRCOUNT`＋`SPLIT`） | 4 |

- 読み書きは誤差の範囲で同じ。
- **末尾への追加は1回あたり約35ns遅い**（ちょうどの長さへの作り直しのコピーと割り当て）。80件程度のリストでは、ERBの1文の手間（数十ns）と同程度。追加が大量に連続する処理で問題になる場合は、容量を倍々で確保する方式（配列関数に渡す時だけ長さに切り詰める）を再検討する。その場合、CHARADATAはキャラごとの配列とは別に長さを持つ必要があり、変更範囲が広がる。
- TRYSKILL型の処理は約18倍速い。実際のゲームはERB関数の`AUTO_SPLIT`を使うため、差はさらに大きい見込み。

### 見つかった既存の不具合（今回の変更とは別）

- `REF`／`REFBYNAME`命令が、固定長の配列に対しても「書式が間違っています」になる（`ArgumentBuilder.cs`の`SP_REF_ArgumentBuilder`）。このため`REF`の参照先ガードはフィクスチャで確認できていない。
- キャラ変数に対する`MATCH`は、固定長の配列でも一致を数えない（0を返す）。今回の範囲外のため未調査。
- `SPLIT`の出力先にキャラ変数を書くと、常にキャラ0へ書き込まれる（もともとの作り）。
