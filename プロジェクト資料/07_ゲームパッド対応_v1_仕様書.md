# Emuera.NET ゲームパッド対応 v1 仕様書

最終更新: 2026-08-16（最新mainへの正式統合を反映）
機能版: Gamepad Support v1 / Gamepad Key Config v1
状態: 最新main統合済み・キーコンフィグ正式採用・配布版

## 1. 目的

Emuera単体で、Windowsの一般的なゲームパッドから既存ゲームの選択UIを操作できるようにする。DS4Windows、Steam Input、JoyToKey等の外部ツールは必須にしない。ゲーム側のERB、CSV、セーブ形式は変更しない。

対象は次のとおり。

- Xbox / XInputコントローラ
- PS4 / DualShock 4系コントローラ
- PS4互換コントローラ
- `joy.cpl`で認識されるDirectInput / HIDゲームパッド

## 2. 入力APIと自動選択

優先順位は次のとおり。

1. XInput #0～#3を確認し、最初に状態取得へ成功したものを使用する
2. XInputがなければWinMM #0～`joyGetNumDevs()-1`を列挙する
3. `joyGetDevCaps`だけでなく`joyGetPosEx`が成功し、ボタン数が1以上または軸数が2以上のデバイスを使用する
4. WinMMで取得できない場合はRaw Input / HIDをフォールバックとして使用する

デバイス名だけで接続可否を決めない。`Microsoft PC ジョイスティック ドライバー`という名前でも、実入力取得に成功すれば有効なゲームパッドとして扱う。同じ物理デバイスが複数APIに見える場合は、上記優先順位により1つの入力Backendだけを使用する。

デバイス列挙と33ms周期の入力ポーリングを分離し、毎回WMI検索や全デバイス列挙を行わない。切断・再接続時だけ一定間隔で再探索する。

## 3. 標準マッピング

| 論理操作 | XInput | PS4系の概念 | Emueraでの動作 |
|---|---|---|---|
| Confirm | A | × | 現在選択中のボタンを決定 |
| Cancel | B | ○ | 意味上のBack/CANCELを実行 |
| FaceWest | X | □ | ゲームパッド設定を開く（初期配置。変更可能） |
| Escape / fast-forward | Y | △ | ESC / マウス右クリック相当。会話・戦闘中の表示や待機を高速処理し、次の入力地点まで進む |
| Previous page / log | LB | L1 | 有効なIndexed / Directional Page UIでは前ページ、Page UIがない時はログを上へ移動 |
| Next page / log | RB | R1 | 有効なIndexed / Directional Page UIでは次ページ、Page UIがない時はログを下へ移動 |
| OPTIONS / Start | Start | OPTIONS | ゲーム中は初期未割り当て。設定で残りの任意Actionへ割り当て可能 |
| Navigation | D-pad / left stick | 十字キー / 左スティック | UIフォーカス移動 |

PS4本体の地域別決定文化には合わせず、v1では×を決定、○をキャンセルとする。XInputは常にXbox配列であり、他の接続済みパッドによって変化しない。

### 3.1 Gamepad Key Config v1

既存の設定画面に「ゲームパッド」タブを追加し、次の9機能をPS/Xbox共通の物理位置名で変更できる。設定は既存の`setting_user.json`へ保存し、未設定・未知の値は標準配置へフォールバックする。

- 決定、戻る・キャンセル、高速送り、前ページ、次ページ、ゲームパッド設定を開く、マクロ実行1～3
- 選択肢は未割り当て、FaceSouth、FaceEast、FaceWest、FaceNorth、LeftShoulder、RightShoulder、Start
- OPTIONS / Startはゲームパッド設定画面では固定の保存ショートカット。Direct Button Capture中は保存せず、割り当て対象の物理ボタンとして捕捉する
- 同じ物理ボタンを選ぶと既存割り当てと自動的に入れ替える。未割り当ても許可する
- 初期配置では□ / X（FaceWest）がゲームパッド設定を開く。マウスの「設定→ゲームパッド」からも復旧できる
- D-pad / Left Stickはキーコンフィグ対象外の固定操作

設定変更は保存時にだけ本番Mappingへ反映し、キャンセル時は破棄する。設定画面では既存のGamepadManagerを共有し、MainWindowとConfigDialogが同時に入力をポーリングしない。

Binding行でConfirmを押すと、Capture開始に使ったボタンを誤登録しないよう全対象ボタンのReleaseを待ってから、次の単一Physical Buttonを割り当てる。Capture中は対象欄へ「ボタンを押してください...」をOverlay表示し、D-pad左で取消できる。Capture対象外のD-pad / Left Stickは固定操作のままとする。

WinMMのPS4配列（button 1 = ×/Confirm、button 2 = ○/Cancel）は、選択中のWinMMデバイス自身がPS4系だと確認できる場合だけ選ぶ。Raw InputにPS4系候補が存在するだけでは、別のWinMMデバイスをPS4配列にしない。WinMM自身のVID/PID、Registry/OEM文字列、固有名、または候補が双方1台だけの一意な既知プロファイルで対応付ける。既知プロファイルのgeneric名は`Microsoft PC ジョイスティック ドライバー`または英語名`Microsoft PC Joystick Driver`に限定する。判定不能な複数デバイス環境ではXbox配列を安全側の既定にし、必要時は次で明示指定する。

```powershell
Emuera.exe --GamepadLayout Auto
Emuera.exe --GamepadLayout Xbox
Emuera.exe --GamepadLayout PlayStationWinMM
```

環境変数`EMUERA_GAMEPAD_LAYOUT`でも同じ指定ができる。overrideは非XInputだけに適用する。

## 4. UI Navigation

現在のInputRequestに属するクリック可能要素を`GamepadFocusTarget`へ変換し、`GamepadNavigationGraph`が画面更新時だけ上下左右リンクを構築する。

対象UI:

- 通常の`ConsoleButtonString`
- 複数列の通常Console行
- HTML_PRINTによるHTML UI
- HTML Island
- INPUTMOUSEKEY / PrimitiveMouseKey

通常Consoleは`ParentLine.LineNo`を優先して行を決める。HTMLは描画済みBoundsから視覚行を作る。上下移動は同じXレーンの候補を優先し、途中行に別列しかない場合は同じレーンが見つかるまで先の行を検索する。左右移動は同一視覚行を基本とする。

そのため縦リンクは必ず隣接Rowへ進むとは限らない。Downは下側の任意の後続Row、Upは上側の任意の前行が有効であり、診断もこのRow skipを正常として扱う。通常Consoleでは構造上の別行が同じ描画Boundsを共有できるため、縦診断は描画YではなくRowを基準にする。ただし逆方向のリンク、異なるSource/Base groupへのリンクは警告する。

### 4.1 Interactive Targetの判定

通常Consoleでは、Emueraが実際のクリック・決定対象として生成した`ConsoleButtonString.IsButton=true`を1つの`GamepadFocusTarget`へ変換する。子の`ConsoleStyledString`、`IsButton=false`の説明文、装飾文、空行はTargetにしない。判定にInput値は使わないため、`Input=0`の正常なボタンはそのまま選択可能である。

表示折り返し・分割後に、説明断片を含む同一論理ボタンが複数の`ConsoleButtonString`インスタンスとして現れる場合がある。この場合は、同じInput/Inputs、同じGeneration、同じSource/Layout/Base group、連続または近接したLineNo/Y、類似したX/幅を満たす隣接断片だけを1つへ統合する。Input番号だけで全画面を統合してはならない。水平に並ぶ同番号ボタン、遠い別領域、別グループは別Targetのまま保持する。

統合Targetは最初（通常は最上段）の断片を代表`Button`とし、描画矩形だけを全断片のUnionにする。これによりフォーカス表示は論理ボタン全体を覆い、Confirm/semantic Back/INPUTMOUSEKEYは従来の代表`ConsoleButtonString`を既存の共通実行経路へ渡す。`--GamepadDebug`では`Logical button group: input=..., fragments=..., representativeLine=..., lines=...`を出力する。

### 4.1.1 HTML modal popupのNavigation scope

`PrintHTMLIsland(depth)`の`depth`は`_htmlElementListDict`の描画順を表すため、番号を固定せずbackdropとの相対順でmodalを判定する。次の条件を満たすHTML IslandのBack/Cancel Targetをmodal backdrop候補とする。

- TargetのBoundsがviewportの大部分を覆う
- Targetが現在InputRequestのBack/Cancel semanticsである
- そのTargetより前面の深度に、enabledなnon-Back HTML Targetが存在する

候補が成立した場合、前面深度のHTML Island groupをactive modal scopeとし、scope外のTargetへ`IsDirectionalFocusExcluded`を設定する。除外TargetはTarget一覧から削除しない。したがって、マウスのpopup外クリックと、明示された背景Cancelのsemantic Backは引き続き利用できるが、背景overlayは通常の上下左右Navigation・初期Focus・Post-Confirm復元の候補にならない。

modal scope内では最初のenabled non-Back Targetを初期Focusとする。今回の`[0] はい`、`[1] いいえ`は同じforeground group内でGraphを構築するため、初期Focusは0番、Down/Upは0↔1、×は現在のConsoleButtonStringを通常決定する。○は既存のBack検索を使い、`input=キャンセル`もsemantic Backとして実行する。

巨大なHTML Buttonというサイズだけでは除外しない。foreground scopeが存在しない場合は通常Targetとして残す。関係のない複数HTML Islandも、backdrop条件が成立しない限り自動的に一方を無効化しない。

HTML_PRINT、HTML Island、INPUTMOUSEKEYは既存のクリック可能要素を対象とし、HTML Buttonと通常HTMLテキストを区別する。

### 4.1.2 LB/RBのsemantic Page Navigation

LB/RBは、現在のInputRequest内で次の全条件を満たす場合だけページ切替に使う。それ以外は従来どおりログスクロールにフォールバックする。

- Interactive `GamepadFocusTarget`の表示ラベルを`NormalizationForm.FormKC`で正規化し、`PAGE.0`または`PAGE 0`形式からページ番号を抽出できる
- 同じSource / Base group / NavigationGroup内に、番号が重複しないPAGE Targetが2個以上ある
- PAGEという単語を含むだけの説明文、`ヒント`等の非PAGE Targetは含めない
- 各PAGE Targetに表示スタイルがあり、`Config.ForeColor`と異なるスタイルのTargetがただ1つだけある

最後の条件はゲーム固有の色名やInput番号を使わず、実際のUIが示す現在ページ印を読むもの。ShinEraTenseiPの該当UIは、すべての`PRINTBUTTON @"[{LCOUNT+100}] PAGE.{LCOUNT}"`を生成し、現在ページだけ`SETCOLOR(... COLOR("aqua") ...)`、それ以外を`GETDEFCOLOR()`で描画しているため、初回表示から現在ページを一意に判定できる。

対象は番号順に並べ、RBは次、LBは前のTargetを`ExecuteGamepadFocusTarget`と同じ既存実行経路へ渡す。入力番号をキーボード入力として模倣しない。先頭でLB、末尾でRBは何もしない（ログスクロールへは流さない）。ページ遷移時はPost-Confirm Focus Anchorを破棄し、PAGE Button自体をFocus履歴に残さないため、次画面は既存の通常Focus復元規則に従う。

modal scopeがある場合はforegroundだけを検索する。modal背後のPAGE Targetは対象にせず、modal内に安全に判定できるPAGE群がない場合はログスクロールへフォールバックする。

Page Navigationには次の2方式がある。

- **Indexed型**: `PAGE.0`、`PAGE.1`、`PAGE 2`などの表示ラベルを正規化して番号を抽出する。同じSource / Base group / NavigationGroupに2個以上のTargetがあり、現在ページの表示スタイルを一意に判定できる場合だけ有効にする。RBは番号順の次、LBは前を実行する。
- **Directional型**: `前のページ`、`次のページ`、`前ページ`、`次ページ`、`PREVIOUS PAGE`、`NEXT PAGE`などの明示的な表示ラベルを正規化して判定する。片方向のTargetが1個だけ表示されるページ端でも有効にする。`戻る`、`BACK`、`RETURN`、`CANCEL`、`次へ`などはPage Targetにしない。

Directional型では、LB/RBの方向に対応するTargetが存在しない場合も操作を消費して何もしない。ページ端でログスクロールへフォールバックしない。Page UI自体が存在しない場合だけ、従来のログスクロールを使う。どちらの方式もInput番号を判定やキーボード入力の疑似送信に使用せず、`ExecuteGamepadFocusTarget`の既存決定経路へ渡す。肩ボタン操作でPage ButtonへFocus履歴を移動させない。

### 4.2 Confirm後の同一画面フォーカス維持

ON/OFF設定など、×決定後に同じ画面をERBが再描画して新しいInputRequestを作る場合に限り、決定直前のTarget一覧を短命なPostConfirm Focus Anchorとして保持する。次のGraph再構築で、対象数の差が許容範囲内かつ、入力値・Source/Base group・Back属性・Boundsの一致が多数ある場合を同一画面とみなす。

同一画面と判定できた場合は、保存したTargetと同じ入力値、同じSource/Base group、同じBack属性、近いBoundsのTargetを復元する。表示色、選択状態、スタイルは比較しない。保存Targetが消えた場合は、同じSource/Base group・Back属性の同じ縦レーンで下、上、近傍の順にフォールバックする。

同じ入力値だけでは復元しない。対象数・構造・Source/Base group・Boundsが変わった画面、または対象が0件の画面では復元を拒否し、通常の初期フォーカスへ進む。AnchorはConfirm直後だけ生成し、Cancelからは生成しないため、既存の○キャンセル挙動には影響しない。

### 4.3 Return Focus History（別画面から戻った時の復元）

×決定または○のsemantic Backで別画面へ遷移する直前に、現在のFocus Targetと画面構造を`GamepadFocusHistoryEntry`として保存する。画面構造は現在の有効Targetを、modal scope、Input、正規化ラベル、Source/Layout/Base group、NavigationGroup、Back属性、Boundsから作るFingerprintで識別する。Input番号単独では識別しない。

復元優先順位は次のとおり。

1. HTML modalの前面scope
2. ×決定直後に同一画面を再描画した時のPostConfirm Focus Anchor
3. ○のBackで一致したReturn Focus Stack
4. 同一FingerprintのLast Focus Cache
5. その画面の通常初期Focus

Return Stackは最大24件、Last Focus Cacheは最大48画面で、古いエントリから破棄する。×で画面が変わったことを確認してから遷移元をStackへ積み、○で戻った後にStack先頭のFingerprintが現在画面と一致した時だけpopして復元する。別画面、同じInput番号だけが一致する画面、modal前後の別scopeは復元しない。画面内の動的な項目が少数増減しても、主要な構造が一致する場合だけ同一画面として扱う。

保存Targetがなくなった場合は、同じSource/Layout/Base groupとBack属性を保って、同じInput、正規化ラベル、同じ縦レーンの下・上、近傍の順に代替Targetを探す。これも見つからなければ通常初期Focusへ戻る。LB/RB Page NavigationはReturn StackとCacheへ記録しないため、ページ切替だけで過去画面の復元履歴が汚れない。

## 5. 決定とキャンセル

×は現在フォーカス中のTargetを`ExecuteGamepadFocusTarget`相当の共通経路へ渡し、マウスクリックまたは通常ボタン決定と同じEmuera内部処理を使う。入力番号をキーボードとして模倣しない。

○は次の順で意味上のBack Targetを検索する。

1. 現在のNavigationGroup
2. 現在Targetと同じSource / Base group
3. 現在のInputRequest全体
4. 見つからない場合だけEsc・右クリック相当

比較用ラベルは`NormalizationForm.FormKC`で正規化し、先頭の`[9]`や`[ 0]`等の装飾を除いて判定する。番号自体はBack判定に使わない。

認識対象例:

- `CANCEL` / `ＣＡＮＣＥＬ`
- `BACK` / `ＢＡＣＫ`
- `RETURN` / `ＲＥＴＵＲＮ`
- `EXIT` / `QUIT`
- 戻る、帰る、キャンセル、閉じる、やめる、店を出る、中止、取消

## 6. 直接入力

十字キーは常にUI Navigationに使用する。左スティックは、現在の1文字入力待ちが方向入力セットを明示している場合だけ直接入力を優先し、それ以外はUI Navigationへ戻す。Raw InputでもHat/POVとX/Y軸を混在させず、物理D-padは`DirectionSource.DPad`、物理左スティックは`DirectionSource.LeftStick`として同じ処理へ渡す。

プロファイル:

- `Auto`（既定）
- `Wasd`
- `Numpad8462`
- `ArrowKeys`
- `Disabled`

指定方法は`--GamepadDirectInput <profile>`または環境変数`EMUERA_GAMEPAD_DIRECT_INPUT`とする。

## 7. 診断

`--GamepadDebug`または`EMUERA_GAMEPAD_DEBUG=1`で、EXEと同じフォルダの`gamepad-debug.log`へ次を記録する。

- XInput #0～#3の状態
- WinMM全indexのCapabilities、戻り値、軸、ボタン、POV
- Raw Input候補のPath、VID、PID、Usage Page、Usage、名前
- 採用Backendとデバイス名
- Face Button Layout、WinMM JoyIdまたはRaw Input VID/PID、選択理由
- Raw Input reportのDPad方向とLeftStick方向（値が変化した場合のみ）
- 値が変わったときの軸・POV・ボタン状態
- Focus Target、行・列・NavigationGroup、上下左右リンク
- Confirm直前のFocus Anchor、次InputRequest、同一画面比較、復元または拒否理由
- Return Focus Stackのpush/pop、Fingerprint一致・不一致、Cache復元、選んだ復元Targetとフォールバック理由
- Confirm、Cancel、semantic Back候補と実行経路
- LB/RBのPAGE候補、現在ページ判定、選択先または端・ログスクロールフォールバック理由
- Alt+Tab復帰、Raw Input再登録、再探索結果

## 8. 起動ライフサイクル

Emuera本来の起動表示を変更しない。`MainWindow`コンストラクタ中にGamepadManagerを生成せず、初回表示前にRaw Input登録やTimer開始を行わない。

起動順:

`通常のフォーム表示` → `Shown / Init` → `console.Initialize()` → `CompleteStartup()` → `BeginInvoke` → `GamepadManager生成` → `Raw Input登録` → `Timer開始`

Opacity、Overlay、Loading画面、`Thread.Sleep`、固定時間待機は使用しない。Handle再作成時は、ゲームパッド初期化済みの場合だけRaw Inputを再登録する。

## 9. v1の受け入れ条件

- Releaseビルドが0エラーで成功する
- StartupTestModeが正常終了し、警告Lv2が0件である
- XInput、WinMM、Raw Inputのいずれか1Backendだけから入力される
- PS4系で×決定、○キャンセル、十字キー、左スティック、L1/R1、OPTIONSが動作する
- 通常Console、HTML、INPUTMOUSEKEYで選択と決定が動作する
- 全角CANCELを○で実行できる
- 起動後接続、切断、再接続、Alt+Tabでクラッシュ・入力停止しない
- Raw InputでもD-padはUI Navigation、左スティックはDirect Inputを優先する
- 正常な同一レーンのRow skipをNavigation Graph診断が警告しない。逆方向リンクは警告する
- 説明文・装飾文・空行がFocus Targetにならず、通常Consoleの0→1がDown 1回で移動する
- クリック可能な複数行断片を含む通常Consoleの論理ボタンが1Targetに統合され、0/1/2の各ブロック間だけをDown 1回で移動する
- HTML modalのfullscreen Cancel backdropがDirectional Focusから除外され、foregroundの0/1選択肢へ初期Focus・上下移動・×決定が入る
- HTML modalの背景CancelがTarget一覧と○semantic Backから利用でき、通常のマウス外側クリックも維持される
- modalでない巨大HTML Buttonと独立した複数HTML Islandが自動除外されない
- Input=0の正常な通常ボタンが選択・決定できる
- HTML Button間をNavigationし、通常HTMLテキストでは停止しない
- PAGE.0 / PAGE.1等の現在ページ印を持つ同一UI群では、LB/RBが前後のPAGE Targetを既存決定経路で実行する。PAGE UIがない・現在ページが一意でない画面は従来のログスクロールを維持する
- PAGE先頭のLB・末尾のRBは何もしない。modal中は背後のPAGE Targetを実行しない
- `前のページ` / `次のページ`型は片方向Targetが1個だけでも認識し、反対方向の端ではconsume-no-opにする。`戻る`はPrevious Pageに誤認しない
- Directional Page UIがある画面のページ端ではログスクロールへフォールバックせず、Page UIがない通常画面では従来のLB/RBログスクロールを維持する
- ON/OFF切替後に同じ画面が再描画されても、決定直前の項目へフォーカスが戻る
- 連続切替でもフォーカスが維持される
- 別画面および同じ入力番号だけが一致する別画面では、前画面のフォーカスを復元しない
- 別画面から○で戻ると、遷移前にFocusしていた項目へ戻る。A→B→C→B→Aでも各画面のFocusを順に復元する
- modalを閉じると背景画面のFocusを復元する。modal前面のTargetを背景画面のCacheとして誤用しない
- Return Focus Stack / Cacheの対象が消えた場合は、同じ縦レーンまたは近傍の安全なTargetへ移り、別グループへは飛ばない
- PS4系Raw Input候補が別に接続されても、XInput/Generic WinMMのFace Button Layoutが変化しない
- ゲームパッド追加前と同じ起動表示で、追加の白枠・Overlay・不可視時間がない

## 10. v1対象外

- 振動、ライトバー、ジャイロ、タッチパッド
- 複数人同時操作
- 製品ごとのGUIマッピング編集画面
- ゲーム側ERBに依存した画面固有ハードコード
