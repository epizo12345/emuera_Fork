最終更新: 2026-08-23

## 1. 何のプロジェクトか

Emuera.NET `BugFix_Test` を基礎に、個人利用中の大規模ゲーム `eramegaten_p` を安全に動かしながら、次を改善する派生プロジェクトである。

1. 並列ERB解析でまれに出る偽の起動警告をなくす
2. EXE起動から操作可能になるまでを短縮する
3. 大量入力マクロの実行時間を短縮する
4. マウスの戻る・進むボタンでゲーム内の前後ページを選べるようにする
5. Ctrl+Cまたはメニューから大量ログを開く待ち時間と、閉じた後の不要な保持を減らす

速度優先だが、セーブ、ERB評価、乱数、入力順、待機命令、最終状態の後方互換性が上位条件である。

## 4. 次にやること

次の最優先課題は、起動後約2.3GB、通常プレイで約3.3GBまで上昇してplateauするmemoryについて、allocation量ではなくlive / retained / committedの内訳を直接profilingすることである。Workstation GCは正式採用していない。

次の順序で検収と保留作業を進める。

1. 最終通常版を実ゲームで数日使い、起動警告、ページ操作、マクロ中断、再帰関数、長時間稼働の不具合を収集する
2. 再現する問題があれば、最終通常版フォルダを基準として別フォルダに検証版を作る
3. 無改造 `BugFix_Test 7b7dd3bf` と最終通常版のN1000比較が必要なら、セーブ読込完了を外部から確実に判定する方法を整えて再測定する
4. さらなる高速化は、strict fallback条件と既存AngleSharp互換性を壊さない範囲で、別途プロファイル根拠を確認してから検討する

「何となく速そう」な変更は追加しない。現在版は安定性を含む実用上の基準点である。

## 5. 最短の再開手順

### 通常版をビルド

```powershell
dotnet publish .\Emuera.csproj -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true -o .\配布\再発行確認
```

必要ランタイムは .NET 10 Desktop Runtime x64。SDKはビルドPCだけに必要で、プレイヤーPCには不要である。

### 起動試験

```powershell
& '.\Emuera以外(開発補助ツールなど)\起動安定性テスト.ps1' -ExePath '.\配布\再発行確認\Emuera.exe' -Iterations 3 -TimeoutSeconds 90
```

GUI起動の許可ダイアログが出る実行環境では、テスト開始前に許可する。許可待ちはEmueraのハングではない。

### マクロ試験

```powershell
& '.\Emuera以外(開発補助ツールなど)\マクロ性能テスト.ps1' -ExePath '.\配布\再発行確認\Emuera.exe' -RepeatCount 10 -Iterations 1 -TimeoutSeconds 180 -CaptureScreenshots
```

N10で画面と操作を確認してから、N100、N1000、最後にN5000へ進む。最初からN5000を流さない。

### 内部計測版

```powershell
dotnet publish .\Emuera.csproj -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true -p:EnablePerformanceMetrics=true -o .\作業用\計測版
```

通常配布へ `EnablePerformanceMetrics=true` は使わない。`EnableStartupMemoryTrim` はプロジェクト既定値trueで、診断上だけ明示falseにして無効化できる。

## 7. 重要な判断

- 起動キャッシュは「プレイヤーが消す必要のない安全な自動無効化」を前提に試したが、速度改善がないため採用しなかった
- 小規模構成は速度を優先する。大規模構成では起動完了時managed memoryが2 GiB以上の場合だけ、約1秒程度のtradeoffでWorking Setを大幅削減する
- マクロ高速化は実処理省略ではなく描画集約を優先した
- ERBホットパスは、評価順を変える式変形ではなく、処理中だけ専有する一時オブジェクト再利用を採用した
- 一時参照プールは整数・文字列を分離し、スレッドごとに最大64個。再帰中の貸出物は再利用しない
- 単一埋め込み文字列は式を同じ位置で1回評価し、結果と前後の固定文字だけを連結する。複数埋め込みは従来経路のまま
- これ以上の文字列式木の平坦化や関数引数の再利用は互換性リスクが上がるため、明確なプロファイル根拠なしには進めない
- 画面外行の遅延処理などは互換性リスクが高いため、プロファイルで明確な根拠が出るまで保留
- ランダム戦闘で実行量が揺れる。単発の数値だけで採否を決めず、同一条件の複数回と内部区間を確認する
- ログ画面の高速化はログ生成を省かず、表示欄へ設定中の途中再描画だけを止める

## 8. 既知の制約

- サイドボタンは表示文の部分一致または内部入力値の完全一致で探すため、どちらも候補に合わない画面では動作しない
- `setting_user.json` 保存時にサイドボタン用の2項目が追加される
- N5000はこのゲームでは約5分前後かかり、戦闘内容で変動する
- ランダムシードを固定していないため、別起動間の状態ハッシュ完全一致は保証試験に使えない
- 長時間の `GC.GetTotalAllocatedBytes(false)` は高速な概算値の更新境界で大きく揺れるため、割り当て比較は複数回のN100とGC回数を優先する
- 最終EXEはframework-dependentなので、未導入PCには.NET 10 Desktop Runtime x64が必要
