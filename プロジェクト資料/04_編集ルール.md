# 編集ルール

最終更新: 2026-07-31

この文書は、担当者やAIが変わっても守る汎用ルール、Emuera.NET高速・互換版の基本方針、実装者・検収者の役割を定める。

## 1. 根本的な汎用ルール

### 1.1 目的と範囲

1. 依頼された成果を最初に明文化し、関係のない改善へ範囲を広げない
2. 調査、診断、実装、検収、配布を区別する
3. 読み取りだけの依頼で外部状態を変更しない
4. 不可逆または広範な変更は、対象と影響を確認してから行う
5. 不明点は既存ソース、設定、ログ、実行結果から先に調べ、推測だけで仕様を決めない

### 1.2 既存資産の保護

1. 他人または利用者の既存変更を自分の変更とみなさない
2. 対象外ファイルを整形・改名・移動しない
3. 削除前に絶対パスと対象範囲を確認する
4. 退避、コピー、復元手順のない状態で破壊的変更をしない
5. 秘密情報、個人データ、配布権のないゲーム資産を成果物へ含めない

### 1.3 変更の原則

1. 1つの変更は1つの目的に限定する
2. 差分を小さくし、原因と効果を追跡できる形にする
3. 既存の公開仕様とデータ形式を必要なく変えない
4. 互換性を崩す可能性がある場合は、先に検出方法と復元方法を用意する
5. 仮説上の改善と実測した改善を明確に分ける
6. 改善しない変更は残さない

### 1.4 検証と報告

1. 変更前の基準を測ってから変更する
2. 検証条件、入力、データ、回数、環境を記録する
3. 平均だけでなく失敗、外れ値、応答性、メモリ増加も見る
4. 成功した試験だけでなく、未実施・不完全・比較不能な項目も報告する
5. 完了報告は成果物の場所、検証結果、残る制約を含める
6. 文書だけで動作を保証せず、可能な範囲で実バイナリを実データに対して試す

### 1.5 引き継ぎ

1. 「何のプロジェクトか」「今何をしているか」「次に何をするか」を常に分かる状態にする
2. 判断理由を短く残し、失敗した候補を再試行しないようにする
3. 恒久資産と使い捨て生成物を分ける
4. 作業終了時に暫定版と不要ログを整理する

## 2. このプロジェクトの基本方針

優先順位は次のとおり。

1. ゲームが正しく起動し、既存セーブをそのまま使えること
2. 入力、ERB評価、乱数、待機、最終状態の後方互換性
3. 起動時間の短縮
4. 大量入力マクロの短縮
5. UI応答性と中断可能性
6. メモリ削減

速度と互換性が衝突する場合は互換性を選ぶ。メモリ削減で速度が落ちる場合は、危険なメモリ使用量でない限り速度を選ぶ。

### 2.1 禁止事項

- プロジェクト所有者の明示依頼がない状態でのstage、commit、push、外部リポジトリへの公開
- `eramegaten_p` のERB、ERH、CSV、画像の書換え
- セーブ変換または新規ゲーム開始を前提とする変更
- マクロ記法の変更
- 入力順、ERB関数回数、評価順、乱数消費順の変更
- `WAIT`、`TWAIT`、右クリック、スキップ、中断の意味変更
- 標準動作でマクロ途中のゲーム処理や出力データを丸ごと省くこと
- プレイヤーによるキャッシュ手動削除を必須にすること
- 計測していない「高速化」を最終版へ入れること
- 暫定版を最終版と同じ場所・名前で残すこと

### 2.2 版の分け方

Gitの代わりにフォルダで分ける。

- 基準版: 変更前のEXEまたは固定原本
- 候補版: 1つの最適化だけを入れた名前付きフォルダ
- 計測版: 内部計測を有効化したビルド
- player版: 計測を無効化した利用者向けビルド
- 最終通常版: 採用済み変更だけを含む確定版

候補の採否が決まったら、必要な代表記録だけを恒久配置へ移し、候補版と大量ログを削除する。

## 3. 実装者ルール

### 3.1 作業前

1. `02_引き継ぎ書.md` と `03_資産目録.md` を読む
2. 最終通常版が実ゲームで起動することを確認する
3. 変更対象のコード経路と互換性条件を列挙する
4. 同じセーブ、マクロ、試験回数で変更前を測る
5. 比較版のフォルダ名に目的と順序を入れる

### 3.2 実装中

1. 1候補につき1目的だけを変更する
2. 本体処理と計測処理を分離し、通常版では計測オーバーヘッドをなくす
3. 並列化では共有状態、順序、例外、ログ、乱数を明示的に確認する
4. キャッシュでは入力ファイル、設定、バージョン、実装変更を自動検知して無効化できなければ採用しない
5. UI集約ではゲーム処理、表示データ生成、イベント処理、中断を省かない
6. 一時オブジェクト削減では参照寿命、別名参照、スレッド安全性を確認する
7. ゲームファイルを修正してエンジン不具合を隠さない

### 3.3 実装後

最低限、次の順に進める。

1. Releaseビルド
2. 起動試験3回、警告Lv2 0件
3. マクロN10、画面と中断確認
4. N100を複数回、短い比較
5. 改善が明確ならN1000
6. 最終候補だけN5000
7. player版で再度起動とN10を確認

候補は次のいずれかで不採用とする。

- 総時間が改善しない
- 改善幅が測定揺れ以下
- 起動、セーブ、表示、入力、乱数、待機、中断に互換性リスクがある
- メモリ消費が過度に増える
- UIが無応答になる
- 実装複雑性に対して利益が小さい

不採用時はソースを最終通常版へ戻し、候補版を最終成果物へ混ぜない。

## 4. 検収者ルール

検収者は実装者の説明をそのまま合格根拠にしない。成果物と記録から独立して確認する。

### 4.1 受入確認

1. 対象EXEのSHA-256を確認する
2. ゲームフォルダの既存EXEを退避してから入替える
3. `save219.sav` のハッシュと更新時刻を確認する
4. 起動警告、タイトル到達、入力受付を確認する
5. 既存セーブを変換なしでロードする
6. サイドボタンの成功画面と非対象画面を両方試す
7. N10の終了画面と中断操作を目視する
8. 長い試験ではWindowsの `Responding` とピークメモリも確認する

### 4.2 性能判定

1. 変更前後で同じEXE配置、同じゲーム、同じセーブ、同じマクロを使う
2. N100までは複数回測る
3. ランダム戦闘の実行量差があるため、総時間だけでなくERB回数、乱数回数、表示行数も見る
4. 起動は内部初期化時間とプロセス壁時計を混同しない
5. 計測版の数値とplayer版の体感・スモークを分ける
6. 速度改善があっても警告増加、画面欠落、状態差、無応答があれば不合格

### 4.3 合格条件

- 起動試験が全回成功
- 偽の警告Lv2が再発しない
- 既存セーブを読み込める
- マクロの入力順と意味が維持される
- マクロ終了画面が正常
- 中断可能でウィンドウが応答する
- 比較対象に対して再現性のある速度改善がある
- 最終player版に不要な計測・強制GC・暫定コードがない
- 文書、ハッシュ、差分ZIPが更新されている

## 5. 作業終了チェック

1. 最終EXEを恒久配置へ置いた
2. 採用差分ZIPを原本へ重ねられる階層で作った
3. 仕様書と引き継ぎ書を現状に合わせた
4. 資産目録へ追加・削除を反映した
5. 代表検証記録だけを残した
6. 暫定EXE、失敗候補、展開原本、一時プロファイルを削除した
7. ゲーム・セーブ・旧EXEを削除していない
8. Gitや外部公開を行っていない
