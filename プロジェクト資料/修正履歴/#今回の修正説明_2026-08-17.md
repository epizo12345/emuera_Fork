## Bugfix Phase 5 focused validation

Phase 5では、cleanupとは分離して既存バグを原因別に3段階で検証した。現在のShinEraTenseiP fixtureでは一部の経路が未使用で、focused testで初めて問題を固定できた。

### Phase 5A: VARSIZE / macro parser

#### 原因

`ReadSingleIdentifierWord()`の`macro.IDWord != null`判定が逆で、正常な単一Identifier macroを例外側へ送っていた。逆にIdentifierへ置換できないmacroでは`macro.IDWord.Code`へ進み、NullReferenceExceptionへ至る可能性があった。加えてmacro展開countの位置にoff-by-oneがあり、100段境界と空の`#DEFINE`の置換元欠落判定にも不整合があった。

#### 想定される実害

`VARSIZE`でmacroを使うERBが正常解析できず、条件によってはEmueraのcontrolled errorではなくNREになる。fixtureでは該当利用が未踏だった。

#### 修正内容

単一Identifier判定、展開count境界、空`#DEFINE`の拒否経路を修正した。

#### 検証

Identifier macro + VARSIZE、100段macro、non-Identifier macroのcontrolled error、empty DEFINE rejectionをfocused testで確認した。Release 0 errors / 37 warnings / new warning 0、Normal / Kojo PASS。

### Phase 5B: ARRAYMSORT

#### 原因

3D配列を受け付ける実装がある一方、引数入口で`IsArray2D`を二重判定して3D payloadを拒否していた。またInt64 key比較を差分減算で行っていたため、`long.MinValue` / `long.MaxValue`付近でoverflowし得た。

#### 想定される実害

3D配列を`ARRAYMSORT`へ渡せず、極端なInt64 keyではソート順が静かに壊れる可能性があった。

#### 修正内容

3D判定を正しい入口条件へ戻し、key比較を差分減算ではなく比較結果ベースへ変更した。

#### 検証

Int64 extremesと3D payloadを同時に使うfocused testでPASSを確認した。Release 0 errors / 37 warnings / new warning 0、Normal / Kojo PASS。

### Phase 5C: graphics color

#### 原因

`GGETCOLOR` / `GSETCOLOR`の負座標判定で`p.X < 0`が二重記述され、`p.Y < 0`が抜けていた。`SPRITEGETCOLOR`はshiftと加算の優先順位によりARGB合成式が意図どおりでなかった。

#### 想定される実害

負のY座標がbounds checkをすり抜け、画像処理が不正位置へ進む可能性があった。取得色も正しい`0xAARRGGBB`にならない場合があった。

#### 修正内容

Y下限判定を`p.Y < 0`へ修正し、各ARGB成分を明示的にshiftしてbitwise ORで合成した。

#### 検証

`0xFF112233`を含むgraphics focused testで確認した。Release 0 errors / 37 warnings / new warning 0、Normal / Kojo PASS。

Phase 5の3 source変更はfocused test、Normal/Kojo回帰確認を通過し、正式publishおよび配布版へ反映した。

## Bugfix Phase 9 focused validation

Phase 9では、数値parser、PICKUPCHARAのspecial index tracking、RAND range計算の既存バグを、Phase 8最新mainから3段階で検証・修正した。

### Phase 9A: TOINT / ISNUMERIC / numeric parser

#### 原因

2024年のparse最適化で`readDigits()`がSearchValues化された際、10進・16進・2進が同じ`0-9,A-F,a-f`集合で走査されるようになった。そのため10進の指数記号`e/E`まで仮数側のdigitとして消費される回帰が生じた。さらにsigned decimalのoffset、hex A-F判定、signed exponent、巨大指数のunchecked Int32 cast、ISNUMERICの範囲外exceptionが混在していた。

#### 想定される実害

`TOINT`と`ISNUMERIC`で同じ文字列への判断が一致せず、`TOINT("0xABC")`は変換可能なのに`ISNUMERIC("0xABC")`がfalseになる、`1e+2` / `1e-2`を合法な指数表記として扱えない、巨大指数がwrapして別値として解釈される、といった問題が起きる。`ISNUMERIC`は多数のERBが利用する基礎機能のため、入力判定や分岐の誤りにつながる。

#### 修正内容

SearchValues高速化は維持したまま、decimal digits、hexadecimal digits、binary digitsの桁集合を分離した。signed decimal offset、hex条件、exponent parsing、ISNUMERICの範囲外 semanticsも修正した。

#### 検証

v1では`1e+2`の失敗を再現して停止し、v2で原因を反映した。±12.34、0xABC、1e±2、ERB直接指数リテラル、malformed exponent、huge exponent、out-of-range ISNUMERICを確認し、`PHASE9A_PASS`を得た。Release 0 errors / 35 warnings / new warning 0、Normal / Kojo PASS、InputReady到達、Lv2 warning 0。

### Phase 9B: PICKUPCHARA special index tracking

#### 原因

キャラクター並べ替え中に`pickList`自体を書き換え、その変更済みindexを旧MASTER/TARGET/ASSIとの照合にも使っていた。

#### 想定される実害

PICKUPCHARAで残したキャラクターでも、MASTER/TARGET/ASSIが`-1`になったり、別キャラクターを指したりする可能性があった。旧公式仕様ではこれらはPICKUPCHARA後に自動追随すると明記されている。

#### 修正内容

旧indexではなく元の`CharacterData`参照を保持し、処理後に新indexを検索してspecial indexを再設定するようにした。

#### 検証

3キャラでTARGET=0、ASSI=1、MASTER=2から`PICKUPCHARA 2,0`を実行し、MASTER=0、TARGET=1、ASSI=-1、CHARANUM=2と`PHASE9B_PASS`を確認した。Release 0 errors / 35 warnings / new warning 0、Normal / Kojo PASS。

### Phase 9C: RAND range overflow

#### 原因

`RAND(min,max)`が`max - min`をunchecked Int64で先に計算していたため、数学的な差がInt64.MaxValueを超えると負値などへoverflowし、その値を乱数生成器へ渡す可能性があった。

#### 想定される実害

旧公式仕様ではcontrolled errorにすべき入力が、生の.NET `OverflowException`やArgument系例外へ進む可能性があった。

#### 修正内容

rangeをchecked計算し、overflowをEmueraのCodeEE controlled diagnosticへ変換した。

#### 検証

最大許容rangeで`PHASE9C_BOUNDARY_PASS`を確認し、1超過rangeでは「RANDの最大値と最小値の差が64ビット符号付き整数の最大値を超えています」というEmuera側diagnosticを確認した。raw .NET exceptionやunexpected passは発生しなかった。Release 0 errors / 35 warnings / new warning 0、Normal / Kojo PASS。
