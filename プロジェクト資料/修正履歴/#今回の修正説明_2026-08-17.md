## Bugfix Phase 5 focused validation

Phase 5では、cleanupとは分離して既存バグを原因別に3段階で検証した。現在のShinEraTenseiP fixtureでは一部の経路が未使用で、focused testで初めて問題を固定できた。

### Phase 5A: VARSIZE / macro parser

#### 原因

`ReadSingleIdentifierWord()`の`macro.IDWord != null`判定が逆で、正常な単一Identifier macroを例外側へ送っていた。逆にIdentifierへ置換できないmacroでは`macro.IDWord.Code`へ進み、NullReferenceExceptionへ至る可能性があった。加えてmacro展開countの位置にoff-by-oneがあり、100段境界と空の`#DEFINE`の置換元欠落判定にも不整合があった。

#### 想定される実害

`VARSIZE`でmacroを使うERBが正常解析できず、条件によってはEmueraのcontrolled errorではなくNREになる。fixtureでは該当利用が未踏だった。

#### 修正内容

単一Identifier判定、展開count境界、空`#DEFINE`の拒否経路を修正した。

#### 効果

正常なIdentifier macroは`VARSIZE`へ正しく渡り、非Identifier macroと空定義はNREではなく想定したcontrolled error/rejectionになる。100段境界の展開判定も意図した上限で扱われる。

#### 検証

Identifier macro + VARSIZE、100段macro、non-Identifier macroのcontrolled error、empty DEFINE rejectionをfocused testで確認した。Release 0 errors / 37 warnings / new warning 0、Normal / Kojo PASS。

### Phase 5B: ARRAYMSORT

#### 原因

3D配列を受け付ける実装がある一方、引数入口で`IsArray2D`を二重判定して3D payloadを拒否していた。またInt64 key比較を差分減算で行っていたため、`long.MinValue` / `long.MaxValue`付近でoverflowし得た。

#### 想定される実害

3D配列を`ARRAYMSORT`へ渡せず、極端なInt64 keyではソート順が静かに壊れる可能性があった。

#### 修正内容

3D判定を正しい入口条件へ戻し、key比較を差分減算ではなく比較結果ベースへ変更した。

#### 効果

3D payloadは受理され、Int64境界値でもoverflowで順序が壊れず、`ARRAYMSORT`の入力形状とkey順序が正しく維持される。

#### 検証

Int64 extremesと3D payloadを同時に使うfocused testでPASSを確認した。Release 0 errors / 37 warnings / new warning 0、Normal / Kojo PASS。

### Phase 5C: graphics color

#### 原因

`GGETCOLOR` / `GSETCOLOR`の負座標判定で`p.X < 0`が二重記述され、`p.Y < 0`が抜けていた。`SPRITEGETCOLOR`はshiftと加算の優先順位によりARGB合成式が意図どおりでなかった。

#### 想定される実害

負のY座標がbounds checkをすり抜け、画像処理が不正位置へ進む可能性があった。取得色も正しい`0xAARRGGBB`にならない場合があった。

#### 修正内容

Y下限判定を`p.Y < 0`へ修正し、各ARGB成分を明示的にshiftしてbitwise ORで合成した。

#### 効果

負のY座標はX座標と同じくbounds checkで拒否され、`SPRITEGETCOLOR`は各成分を正しい`0xAARRGGBB`位置へ合成する。

#### 検証

`0xFF112233`を含むgraphics focused testで確認した。Release 0 errors / 37 warnings / new warning 0、Normal / Kojo PASS。

Phase 5の3 source変更はfocused test、Normal/Kojo回帰確認を通過し、正式publishおよび配布版へ反映した。

### Phase 7B: VariableSize dimension overflow

#### 原因

#### 想定される実害

#### 修正内容

#### 効果

#### 検証

`DA,65536,65536`と`TA,2048,2048,2048`をpatched版だけで実行し、OOMや巨大allocationに進まずInputReadyまで到達することを確認した。コード上でもlongによる要素数上限判定後にreturnすることを確認した。startup captureには上限超過warning本文が含まれなかったため、警告文言そのものの確認は行っていない。安全上、未修正版での巨大allocation再現テストは実施していない。Normal/Kojo PASS。

### Phase 7C: CircularBuffer.Clear

#### 原因

#### 想定される実害

#### 検証

## Bugfix Phase 8 focused validation

Phase 8では、演算子評価と文字列比較の既存バグをfocused test付きで修正した。

### Phase 8A: unary minus operand evaluation

#### 原因

operandを一度`ret`へ評価した後、returnで同じoperandをもう一度`GetIntValue()`していた。

#### 想定される実害

`-RAND(...)`なら乱数を余分に消費し、副作用関数なら処理が2回実行されてゲーム状態まで変わる可能性があった。fixtureでも関数結果への単項マイナスが多数使われていた。

#### 修正内容

取得済み`ret`を反転して返すようにした。

#### 効果

## Bugfix Phase 9 focused validation

Phase 9では、数値parser、PICKUPCHARAのspecial index tracking、RAND range計算の既存バグを、Phase 8最新mainから3段階で検証・修正した。

### Phase 9A: TOINT / ISNUMERIC / numeric parser

#### 原因

2024年のparse最適化で`readDigits()`がSearchValues化された際、10進・16進・2進が同じ`0-9,A-F,a-f`集合で走査されるようになった。そのため10進の指数記号`e/E`まで仮数側のdigitとして消費される回帰が生じた。さらにsigned decimalのoffset、hex A-F判定、signed exponent、巨大指数のunchecked Int32 cast、ISNUMERICの範囲外exceptionが混在していた。

#### 想定される実害

`TOINT`と`ISNUMERIC`で同じ文字列への判断が一致せず、`TOINT("0xABC")`は変換可能なのに`ISNUMERIC("0xABC")`がfalseになる、`1e+2` / `1e-2`を合法な指数表記として扱えない、巨大指数がwrapして別値として解釈される、といった問題が起きる。`ISNUMERIC`は多数のERBが利用する基礎機能のため、入力判定や分岐の誤りにつながる。

#### 修正内容

SearchValues高速化は維持したまま、decimal digits、hexadecimal digits、binary digitsの桁集合を分離した。signed decimal offset、hex条件、exponent parsing、ISNUMERICの範囲外 semanticsも修正した。

#### 効果

`TOINT`と`ISNUMERIC`の判定が同じ入力規則に従い、指数・hex・binary・範囲外入力が誤変換やraw exceptionへ流れず、ERB側の数値判定とcontrolled errorが一貫する。

#### 検証

v1では`1e+2`の失敗を再現して停止し、v2で原因を反映した。±12.34、0xABC、1e±2、ERB直接指数リテラル、malformed exponent、huge exponent、out-of-range ISNUMERICを確認し、`PHASE9A_PASS`を得た。Release 0 errors / 35 warnings / new warning 0、Normal / Kojo PASS、InputReady到達、Lv2 warning 0。

### Phase 9B: PICKUPCHARA special index tracking

#### 原因

キャラクター並べ替え中に`pickList`自体を書き換え、その変更済みindexを旧MASTER/TARGET/ASSIとの照合にも使っていた。

#### 想定される実害

PICKUPCHARAで残したキャラクターでも、MASTER/TARGET/ASSIが`-1`になったり、別キャラクターを指したりする可能性があった。旧公式仕様ではこれらはPICKUPCHARA後に自動追随すると明記されている。

#### 修正内容

旧indexではなく元の`CharacterData`参照を保持し、処理後に新indexを検索してspecial indexを再設定するようにした。

#### 効果

PICKUPCHARA後もMASTER/TARGET/ASSIが同じキャラクターを指し続け、削除された対象だけ`-1`になる。並べ替えによるindex変化で別キャラクターへ結び付く誤判定を防ぐ。

#### 検証

3キャラでTARGET=0、ASSI=1、MASTER=2から`PICKUPCHARA 2,0`を実行し、MASTER=0、TARGET=1、ASSI=-1、CHARANUM=2と`PHASE9B_PASS`を確認した。Release 0 errors / 35 warnings / new warning 0、Normal / Kojo PASS。

### Phase 9C: RAND range overflow

#### 原因

`RAND(min,max)`が`max - min`をunchecked Int64で先に計算していたため、数学的な差がInt64.MaxValueを超えると負値などへoverflowし、その値を乱数生成器へ渡す可能性があった。

#### 想定される実害

旧公式仕様ではcontrolled errorにすべき入力が、生の.NET `OverflowException`やArgument系例外へ進む可能性があった。

#### 修正内容

rangeをchecked計算し、overflowをEmueraのCodeEE controlled diagnosticへ変換した。

#### 効果

許容範囲内のRANDは従来どおり実行され、範囲超過はraw .NET exceptionやunexpectedな乱数実行ではなくEmueraのcontrolled errorになる。

#### 検証

最大許容rangeで`PHASE9C_BOUNDARY_PASS`を確認し、1超過rangeでは「RANDの最大値と最小値の差が64ビット符号付き整数の最大値を超えています」というEmuera側diagnosticを確認した。raw .NET exceptionやunexpected passは発生しなかった。Release 0 errors / 35 warnings / new warning 0、Normal / Kojo PASS。

## Bugfix Phase 10A: POWERの整数精度・境界値修正

### 原因

式中関数`POWER(x,y)`と旧`POWER`命令の両方が、Int64の引数を`double`へ変換して`Math.Pow`で計算し、最後に`long`へcastしていた。`double`で整数を完全に表現できるのは53bit程度までのため、2^53を超える領域ではInt64として正確な結果でも丸め誤差が発生していた。double化した値で境界判定を行っていたため、`POWER(__INT_MAX__,1)`、`POWER(__INT_MIN__,1)`、`POWER(-2,63)`のように数学的結果がInt64範囲内でも範囲外エラーになる場合があり、巨大指数では`-1`の累乗の奇偶性を失う可能性もあった。

### 想定される実害

POWERを整数関数として利用するERBで、大きな値が正しい結果からずれる、1乗だけでも入力値が変化する、本来有効なInt64境界値をエラー扱いする、大きな指数で符号が誤るといった問題が起こり得た。ShinEraTenseiP fixtureにもPOWERの使用箇所があるため、動的な引数が大きくなる経路では実害になり得る。

### 修正内容

計算本体から`Math.Pow(double)`を廃止し、`ExpressionMediator.CalculatePower(long x, long y)`へ共通化した。指数が0以上の場合はchecked Int64 arithmeticによるexponentiation by squaring（二乗法）で計算し、Int64範囲を超えた場合だけCodeEEへ変換する。負指数は従来の整数返却挙動を維持し、`0`の負指数は無限大のcontrolled errorとした。指数`long.MinValue`でも符号反転を行わないため、指数処理自体のOverflowExceptionを避けている。なおoverflow診断文字列生成に残る`Math.Pow`はエラーメッセージ用で、正常計算には使用しない。

### 効果

2^53を超える整数、Int64境界値、巨大指数でも、整数として正しい結果またはEmueraのcontrolled errorへ進み、double丸めによる誤結果・誤範囲判定・符号誤りを避ける。

### 検証

baselineで`POWER(3,34)`の精度不具合と、Int64境界値の誤判定を再現した。patched focused testでは`PHASE10A_PASS`を確認し、2^53超の1乗、Int64上下限、`(-2)^63`、巨大な`-1`指数、負指数、`0^0`、式中関数版と旧命令版を検証した。`POWER(2,63)`はcontrolled overflow error、`POWER(0,-1)`は従来どおり「累乗結果が無限大です」のcontrolled errorとなった。Release 0 errors / 35 warnings / new warning 0、Normal / Kojo PASS、Init:End到達、Lv2 warning 0。

Phase 10Aは正式publishおよび配布版へ反映した。

## Memory Optimization Phase 10B: 起動後retained memory削減

### 背景 / 原因

大規模ERB/口上の解析後、InstructionLineは`JumpToEndCatch`、`IfCaseList`、`dataList`、`callList`のreference slotを個別に保持していた。これらは命令種類ごとに用途が分かれており、同じInstructionLineで同時利用しないため、使用しないreference slotも全行で常駐していた。また、private variableを持たないFunctionLabelLineでも空のDictionaryが生成され、VOID命令の引数解析では状態を持たない`VoidArgument`が毎回生成されていた。

### 想定される影響

これらは機能上の不具合ではないが、数百万行規模のInstructionLine、約13万の関数ラベルを含む構成では、未使用reference、小さな空Dictionary、同一内容のVOID引数objectが起動後も保持され、managed memory・working set・allocationを押し上げる可能性があった。測定環境やGC状態により実測値は変動するため、起動時間の改善や全環境で同じ削減量になることは主張しない。

### 修正内容

Phase 10B1では`JumpTo`を独立fieldとして維持し、`JumpToEndCatch`、`IfCaseList`、`dataList`、`callList`の4用途だけを`object auxiliaryData`の1referenceへunionした。既存property interfaceと`JumpTo`との同時保持は維持し、sidecar objectは追加していない。

Phase 10B2では`FunctionLabelLine.privateVar`をnull開始にし、`AddPrivateVariable()`の初回呼出し時だけDictionaryを生成する。`GetPrivateVariable`、`ScopeIn`、`ScopeOut`はnullを安全に処理し、private variableを持つ関数の処理は維持した。

Phase 10B3では状態を持たずidentity依存もない`VoidArgument`を`VoidArgument.Instance`として共有した。

### 実測

Kojo fixtureの同一条件3-run中央値を、validation raw dataから再計算した。Baseline → B1 → B1+B2 → B1+B2+B3の値は次のとおり。
