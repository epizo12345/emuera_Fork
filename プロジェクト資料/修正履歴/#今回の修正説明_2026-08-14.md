# ERB起動時allocation削減と解析基盤の整理

## 概要

ERB起動時の解析処理について、既存の挙動・互換性を維持したまま一時オブジェクトの生成量を減らすため、Argument ParserとLexer周辺の内部データ構造を整理した。

主な変更は、`ExpressionParser.ReduceArguments` の一時collectionのList化、`WordCollection` のCompact表現と必要時だけのLinkedListへの遅延変換、Lexer結果用Listの初期確保方法の最適化である。

また、性能調査で継続利用できる汎用profiling機能を `PERFORMANCE_METRICS` ビルド限定で整理した。

今回確認できた主な効果は **allocation削減** である。起動時間・CPU時間については実行順や環境による揺れが大きく、現時点では速度改善率を確定していない。

## 変更方針

今回の最適化では、以下を優先した。

- 既存ERBとの互換性を最優先する。
- ParserやLexerの構文解析ルール自体は変更しない。
- Macro、Pointer、挿入・削除など、既存のnode操作が必要な処理を壊さない。
- allocationを減らせても速度改善が再現しない場合は、速度向上を採用理由にしない。
- 計測専用コードは通常Releaseへ不要なoverheadを持ち込まない。
- Phase固有の一時measurementは検証終了後に撤去し、汎用Profilerだけを残す。

## ReduceArgumentsの一時collectionをList化

`ExpressionParser.ReduceArguments` は、解析した複数の `AExpression` を一時的に保持するために `LinkedList<AExpression>` を使用していた。

この処理で実際に必要だったのは、末尾への追加、末尾要素の参照、順序を保った返却であり、LinkedList固有のnode操作は使っていなかった。

そのため内部collectionを `List<AExpression>` へ変更した。

### 変更前

```csharp
var terms = new LinkedList<AExpression>();
terms.AddLast(...);
return [.. terms];
```

### 変更後

```csharp
var terms = new List<AExpression>();
terms.Add(...);
return terms;
```

これにより、解析ごとに生成されていた `LinkedList<AExpression>` と `LinkedListNode<AExpression>` のallocationを避ける。

Allocation削減は確認できたが、複数回の交互測定では起動時間・ScriptParse時間の改善は安定して再現しなかった。そのため、この変更の速度効果は **UNPROVEN** とする。

## WordCollectionのCompact表現

Lexerが生成するtoken列は従来、基本的に `LinkedList<Word>` とその `LinkedListNode<Word>` で保持していた。

調査の結果、通常の解析ではWordCollectionの大部分が単純な順次追加・順次読み取りだけで終了し、LinkedList nodeの挿入・削除機能を必要とするcollectionは非常に少なかった。

そこで通常状態を、

```text
List<Word> + index cursor
```

とするCompact表現へ変更した。

一方、Macro展開などで以下が必要になった場合だけ、

- `LinkedListNode<Word>`
- Pointerの前後参照
- Insert / InsertRange / Remove
- node identity

既存の `LinkedList<Word>` へ一方向に遅延変換する。

```text
Compact List
    ↓ node操作が必要
EnsureLinked()
    ↓
LinkedList
```

これにより、通常のWordCollectionではLinkedList nodeを生成しない。

## WordCollectionの互換性

Compact化にあたり、単純なList置換では既存挙動が変わる箇所を個別に確認した。

特に以下を維持している。

- `Count`
- `Current`
- `EOL`
- `ShiftNext`
- `PointerReset`
- `Pointer`
- `Collection`
- `Insert`
- `InsertRange`
- `Remove`
- Clone
- Macro展開
- Compact→Linked変換後のcursor
- `Add(WordCollection)` の通常追加

### self-add

旧実装の `wc.Add(wc)` は、LinkedListを列挙中に同じcollectionへ要素を追加するため、最初の追加が行われた後に `InvalidOperationException` が発生する。

Compact Listで単純に `AddRange(this)` とすると、例外を出さず全要素を複製してしまい既存挙動と異なる。

そのためself-addだけは `ReferenceEquals(this, wc)` で旧LinkedList経路へ戻し、例外型・メッセージ・途中まで発生する副作用を含めて旧挙動と一致させた。

## Lexer-only Lazy Capacity-8

Compact化後のfresh profileでは、`List<Word>` のgrowthに伴う `Word[]` allocationと `Array.Copy` が残っていた。

実測では大量口上構成で、

```text
4 → 8 resize
1,241,760回

resize時にコピーされたWord参照
13,032,984 references
```

が確認された。

一方、Lexer結果には0-tokenや1-tokenの小さいcollectionも多いため、全WordCollectionを最初からCapacity 8にすると不要allocationが増える。

そこでLexerが生成するWordCollectionだけを専用のPending状態で開始する。

```text
LexerPending
compactCollection == null
linkedCollection == null
```

tokenが1個も無い場合は、そのまま終了する。

```text
0 token
→ List<Word>を生成しない
→ Word[]も生成しない
```

最初のtokenが実際に追加された時点でのみ、

```csharp
new List<Word>(8)
```

を生成する。

これにより、

```text
0 → 4 → 8
```

だった経路を、

```text
0 → 8
```

にできる。

通常の `new WordCollection()` は従来どおり通常Listで開始し、Lexer以外のcapacity policyは変更していない。

## 並列ERB解析まわり

ERB解析はPrimaryParseや残り関数のScriptParseで並列処理を行う。

今回の性能改善では並列Parserの実行方式を大きく変更せず、既存の安全対策を維持した。

共有error flagの更新など、並列実行中に単純代入で競合し得る箇所についてはthread-safeな更新を使用する。

また、WordCollection Compact化によってMacroやParserのnode操作が必要になった場合も、`EnsureLinked()` で従来のLinkedList semanticsへ戻すため、並列解析のために構文解釈そのものを変更していない。

## 汎用ERB Profiling

性能調査で再利用できる汎用Profilerを残した。

`PERFORMANCE_METRICS` が有効な計測ビルドでは、`--ErbStartupProfile` / `--ErbStartupProfileMode` を利用して、ERB起動処理の詳細情報を取得できる。

主な計測対象は以下。

- ERB stage timing
- PrimaryParse
- ScriptParse
- file単位の読み込み・解析情報
- function単位の解析時間
- `SetArgumentToCalls`
- `ForceSetArgumentCalls`
- FunctionCode別件数
- Label数
- InitiallyParsed
- Remaining
- ParallelRemaining

特定Phaseだけで使用した以下のmeasurementは、役目を終えた時点で削除した。

- Strict Decimal eligibility
- WordCollection mutation / promotion
- List growth / resize / capacity
- Parallel warning diagnostics

通常ReleaseにはPhase固有measurementを残さない。

## 速度評価について

今回の一連の変更ではallocation削減は明確に確認できた。

一方、起動時間については実行順・CPU状態・OS側の影響と思われる揺れが大きく、短いrunでは改善して見えても、交互実行を増やすと同じ結果が再現しないケースがあった。

そのため、

```text
Allocation:
CONFIRMED

Compatibility:
PASS

Speed:
UNPROVEN
```

としている。

今回の変更を「起動時間が○%高速化した」とは扱わない。

## 修正前後のチェックポイントベンチマーク

今回の性能改善をまとめて適用した状態について、
2026-08-13時点のMacro hash collision修正のみを適用した版を比較対象として、
同一ゲームデータ・同一Build条件でBefore/Afterベンチマークを実施した。

比較対象：

- Before: Macro hash collision修正適用済み、今回のERB Parser性能改善は未適用
- After: Beforeに加えて今回のERB Parser性能改善を適用

テスト構成：

- 通常構成（eramegaten_p）
- 大量口上あり構成（eramegaten_p_口上有り）
- Before / After 各5回
- 各fixture内で実行順を交互に配置
- Release / win-x64 / PublishSingleFile
- Startup時間は既存の起動Timing logから取得
- Peak Working Setは外部からプロセスを監視して取得

### 通常構成

| 項目 | Before Median | After Median | 差 |
|---|---:|---:|---:|
| Startup | 2010 ms | 1952 ms | -58 ms (-2.9%) |
| ERB | 1206 ms | 1186 ms | -20 ms (-1.7%) |
| Peak Working Set | 1493 MB | 1344 MB | -149 MB (-10.0%) |

通常構成ではPeak Working Setに比較的大きな削減が確認された。

一方、Startup時間についてはMedianでは改善しているものの、
平均値や実行順を考慮した比較では方向が安定していないため、
今回の5回測定だけから明確な高速化率を確定することはできない。

### 大量口上あり構成

| 項目 | Before Median | After Median | 差 |
|---|---:|---:|---:|
| Startup | 3861 ms | 3788 ms | -73 ms (-1.9%) |
| ERB | 3059 ms | 2921 ms | -138 ms (-4.5%) |
| Peak Working Set | 4196 MB | 4318 MB | +121 MB (+2.9%) |

大量口上あり構成では、
StartupおよびERB解析時間について改善傾向が確認された。

平均値でも、

- Startup: 3883.8 ms → 3775.4 ms（約108 ms短縮）
- ERB: 3088.8 ms → 2989.0 ms（約100 ms短縮）

となっており、大量ERB・大量口上を読み込む構成では
今回のallocation削減が実行時間にも寄与している可能性がある。

ただし、実行順やOS側キャッシュ等による変動が存在するため、
現時点では「約2～4%高速化した」と確定的には扱わず、
「改善傾向を確認」とする。

Peak Working Setについては、
MedianではAfter側が約2.9%大きい一方、
MeanではAfter側が約34 MB小さく、
run間の変動も大きかった。

そのため、大量口上あり構成のPeak Working Setについては
今回の測定から明確な増減は確認できなかった。

### ベンチマーク結果の扱い

今回の測定は5回ずつのチェックポイントベンチマークであり、
最終的な性能評価を目的としたものではない。

現時点で確実に確認できている主な効果は、
個別検証で確認した起動時allocation削減である。

今回の総合ベンチマークからは追加で、

- 通常構成ではPeak Working Set削減の強いシグナル
- 大量口上あり構成ではStartup / ERB解析時間の改善傾向
- Parser errorなし
- Lv2 warningなし
- Release Buildおよび既存ゲーム起動に問題なし

を確認した。

今後さらに性能改善を行った後、
最終版ではより多いrun数と実行順を均衡させた条件で
改めて総合ベンチマークを実施する予定。

## InstructionLine Argument / argprimitive保持領域の統合（Production Adoption）

`InstructionLine` が別々に保持していた `Argument` と `CharStream argprimitive` を、1つの `object` 参照へ統合した。`Argument` getter/setter、`PopArgumentPrimitive` は既存の null・clear・CharStream保持規則を維持する。

検証済みの効果は、Release object size 176 bytes から 168 bytes、起動時allocation約9.8 MB（Normal）／約28.8 MB（Kojo）の削減である。focused semantic、DEBUG null、PopArgumentPrimitive、既存macro、PRINT/FORM・IF/ELSE・CALL・CALLFORM・FOR・REPEATのtargeted runtime smoke、Normal/Kojo startupをPASSとした。N=1000 / N=5000のRuntime検証でも、Argument getterの型判定に起因する明確な性能回帰は確認されなかった。ただし、高速化または性能差ゼロとは断定しない。

本番適用範囲はこの1参照統合だけで、LoopState等の別最適化は含めない。次候補は `LoopEnd` / `LoopCounter` / `LoopStep` の実体と所有権のfeasibility/design分析とする。
