# 今回の修正説明 — 2026-09-15

## 概要

MAIN_OPTで検証済みのM3AとM4Aをlocal mainへ採用した。どちらもゲームの結果、セーブ形式、ERBの評価順を変えず、長時間残る小さな入れ物の無駄を減らす変更である。

## 1. M3A — SET左辺保持の軽量化

### 変更前

SET命令の左辺は、初回の引数解析まで`WordCollection`として保持していた。左辺に必要なのは`Word`の参照と順序だけであり、collection本体を長く残す必要はなかった。

```text
SET左辺 → WordCollection → InstructionLineが初回parseまで保持
```

### 変更後

`WordCollection`をexact-size `Word[]` snapshotへ凍結して保持し、初回parse時だけ既存parser向けの一時`WordCollection`へ戻す。

```text
SET左辺 → WordCollection → exact-size Word[] → 初回parse時の一時WordCollection → 解放
```

`Word`はcloneせず、参照同一性と順序を保つ。`Collection()`や`Pointer()`を呼ばないため、compact collectionのlinked昇格やpointer変更も起こらない。

### なぜ安全か

`Word` reference、Word順序、`Word.IsMacro`、SET左辺→右辺のparse順を維持する。snapshotは初回parseで取り出した直後にslotを`null`へ戻し、旧形式の`WordCollection`が残っていた場合は互換fallbackとして従来どおり扱う。save/load形式も変更していない。

### 実測結果

直接対象型のshallow保持量は25,065,528 bytes、約23.90 MiB減少した。この値は`WordCollection`等の直接対象だけを数えたものであり、ゲーム全体のメモリ削減量ではない。

## 2. M4A — FixedVariableTerm添字配列の共有

### 変更前

長寿命の`FixedVariableTerm`は、添字が1個や2個でも3要素の`long[]`を保持していた。

```text
添字 [5]     → [5, 0, 0]
添字 [5, 10] → [5, 10, 0]
```

### 変更後

`VariableTerm.Restructure()`で確定したexact-size transporterを`FixedVariableTerm`が共有する。

```text
添字 [5]     → [5]
添字 [5, 10] → [5, 10]
```

短い配列にない添字を読む場合は、従来の未使用slotと同じ論理0を返す。存在しない添字へ書く時だけ`long[3]`へcopy-on-writeし、共有元配列は変更しない。通常の短命参照用poolと`Reset`経路は従来どおり3要素配列を使う。

### 論理0とcopy-on-write

```text
[5]      → Index1=5, Index2=0, Index3=0
[5, 10]  → Index1=5, Index2=10, Index3=0

exact-size array
    ↓ 不足位置への書込み時だけ
long[3]へcopy-on-write
```

### なぜ安全か

共有元の`VariableTerm.transporter`は書き換えない。通常の短命参照用pool、empty constructor、`Reset`は従来どおり3要素配列を使う。

### 実測結果

M4D0のモデルでは、保持量の見積りは約6.225 MiB、起動時allocation回避の見積りは約18.806 MiBだった。測定対象が異なるため、この二つを合算しない。heap censusの`System.Int64[]`約7.69 MiBもM4A単独の効果ではなく、補助的な観測値である。
