# MAIN_OPT-M3A / M4A メモリ保持最適化 修正説明

## 背景

main側では`InstructionLine`などの保持メモリをすでに削減していた。MAIN_OPTでは残るretained objectをheap/censusで追い、大量に存在する小さな入れ物の余剰slotやcontainer overheadを、ゲームの互換性を変えずに減らせるか調査した。

M3系ではSET左辺を保持する`WordCollection`、M4系では`FixedVariableTerm`のtransporterがnarrow candidateとして残った。

## M3A — SET左辺保持の軽量化

### 調査

save219ロード後のH1で`assignmentFrozenSnapshot=214,621`、frozen words=881,353、snapshot mismatch=0を確認した。直接対象の`WordCollection` / `List<Word>` / `Word[]`のshallow差は-25,065,528 bytes、約-23.90 MiBだった。この値は対象型に限った値であり、ゲーム全体のメモリ削減量ではない。

### 実装

```text
変更前
InstructionLine
  └─ WordCollection
       └─ List / LinkedList storage

変更後
InstructionLine
  └─ exact-size Word[]
       ↓ 初回SET parse時だけ
     temporary WordCollection
```

SET左辺は初回引数解析までだけ必要なため、`WordCollection`そのものではなく、同じ`Word`参照を同じ順序で並べたexact-size `Word[]` snapshotを保持する。初回SET parse時だけ既存parser向けの一時`WordCollection`へ戻し、その後snapshot slotを解放する。

### 互換性

`Word` reference identity、Word順序、`Word.IsMacro`、SET左辺→右辺のparse順、save/loadを維持する。Word clone、compact→linked promotion、pointer変更は行わない。旧形式の`WordCollection`は互換fallbackとして扱う。

### 効果

直接対象型のshallow保持量は約23.90 MiB減少した。whole-process heapや別測定の数値をM3A単独効果として加算・帰属していない。

### 検証

M3A focused snapshot test、normal Release、`PERFORMANCE_METRICS` Release、決定論的N100/N1000 semantic validationをPASSした。

### 採用状態

M3Aは`7fbac4be214cd5ae61a5c4d653033ee79028c489`でmainへ正式採用し、M3A/M4A反映版の正式配布EXEへ含めた。

## M4A — FixedVariableTerm添字配列の軽量化

### 調査

construction censusでは`fromArgsTotal=410,828`であり、transporter長は0/1/2/3要素が4,597 / 396,879 / 9,344 / 8だった。大半が1要素であるため、常に`long[3]`へcopyする未使用slotが候補になった。

### 実装

```text
変更前
VariableTerm.transporter
      ↓ copy
FixedVariableTerm long[3]

変更後
VariableTerm exact-size transporter
      ↓ share
FixedVariableTerm exact-size long[]
```

`VariableTerm.Restructure()`で定数添字が確定したとき、`FixedVariableTerm`はexact-size transporterをcopyせず共有する。

### 互換性

```text
[5]      → Index1=5, Index2=0, Index3=0
[5, 10]  → Index1=5, Index2=10, Index3=0

不足位置への書込み時だけ long[3] へcopy-on-write
```

存在しない添字の読取りは従来の未使用slotと同じ論理0である。書込み時だけ`long[3]`へcopy-on-writeし、共有元配列は変更しない。通常pool、empty constructor、`Reset`は従来どおり3要素配列を使う。

### 効果

M4D0/M4Aモデルのretained削減候補は約6.225 MiB、startup allocation回避候補は約18.806 MiBである。測定対象が異なるため合算しない。heapの`System.Int64[]`差約7.69 MiBは補強証拠であり、M4A単独の厳密payload値ではない。

### 検証

M4A shared exact transporter focused test、normal Release、`PERFORMANCE_METRICS` Release、決定論的N100/N1000 semantic validationをPASSした。H0/H1/N100で`shortTransporterCowExpansionCount=0`を確認した。

### 採用状態

M4Aは`57a160e6f2871f28951e95bad68e3279f59e05a0`でmainへ正式採用し、M3A/M4A反映版の正式配布EXEへ含めた。
