# 今回の修正説明 2026-08-15

## 概要

2026-08-15の更新では、Emuera.NETのERB読み込み時に発生していた一時オブジェクト生成を追加で削減し、さらに大量のERB・口上ファイルを含む構成で起動完了後のメモリ使用量を整理する処理を追加した。

今回の変更は、ERBの構文・ゲーム処理・セーブデータ形式を変更するものではない。主な目的は、

- 起動中に作ってすぐ破棄される一時オブジェクトを減らす
- GCへ渡される短命オブジェクト量を減らす
- 大規模構成で起動後も大きく残るWorking Setを必要に応じて縮小する

ことである。

性能値はNormal構成と大量口上構成（Kojo）で個別に検証した。単発値や異なる段階の結果を単純合算して「総合で何%高速化した」とは扱わない。

## CharStreamの不要な生成削減

`EraStreamReader.ReadEnabledLine()` 内で、読み込み途中に何度も生成していた `CharStream` を、外部へescapeする前の範囲に限定して `Reset(string)` により再利用するよう変更した。

共有poolやstatic cacheは使用せず、1回の読み込み処理内だけで再利用するため、既存のownershipや並列解析の意味論を変更しない。

検証時のTotal managed allocationは、

- Normal: 約71.1 MB削減（約3.04%）
- Kojo: 約244.1 MB削減（約3.86%）

だった。

Startupの複数run比較では、Candidate固有の明確な性能退行は確認されなかった。

## ReadStringの単純文字列fast path

`LexicalAnalyzer.ReadString()` は従来、escape文字を含まない単純な文字列でも必ず `StringBuilder` とその内部バッファを生成していた。

変更後は、まず文字列を直接走査し、

- `\` を含まない場合は `StringBuilder` を生成せず結果文字列を作る
- `\` を検出した場合のみ従来相当のescape処理へfallbackする

ようにした。

escape、終端文字、Unicode、trailing backslash、非ゼロpointer等を含むfocused検証でBaseline/Candidateの結果・最終pointer・例外分類が一致することを確認した。

検証時のTotal managed allocationは、

- Normal: 約383.2 MB削減（約16.91%）
- Kojo: 約404.8 MB削減（約6.66%）

だった。

GC collection数にも改善が見られたが、起動速度については「高速化した」とは断定しない。複数runでは全体として明確な一貫したStartup regressionは確認されなかった。

## 行頭命令解析の一時IdentifierWord削減

ERB各行の先頭命令名を読む処理では、従来、

1. 命令名のstringを生成
2. そのstringを保持する `IdentifierWord` を生成
3. 呼び出し側が直後に `.Code` から同じstringを取り出す

という経路になっていた。

`IdentifierWord` のconstructorはstringを保持するだけで、この呼び出し経路ではwrapper自体に追加の意味がなかったため、同じstringを直接命令判定へ渡すよう変更した。

`ReadFirstIdentifierWord()` 自体は残しており、別経路の互換性は維持している。

検証時のTotal managed allocationは、

- Normal: 約30.0 MB削減（約1.59%）
- Kojo: 約138.5 MB削減（約2.44%）

だった。

Normal/Kojo双方でRelease build・Startup・Parser error・Lv2 warning・Exception/Crashを確認し、問題は発生しなかった。

## 起動後メモリの調査

タスクマネージャー上で、大量口上構成のEmueraが起動後も4 GB前後のメモリを使用しているように見える状態を調査した。

起動処理では既に `Preload.Clear()` が行われていたため、先読みデータを意図的に保持し続けているわけではなかった。

一方、参照解除後も通常のGCタイミングではメモリがすぐに回収・decommitされず、Working Setが大きく残ることが確認された。

Aggressive / blocking / compacting full GCを診断的に実行したところ、大量口上構成ではWorking Setが約4.09 GBから約2.64 GBまで低下した。

この結果から、起動後の大きなWorking Setの相当部分は、ゲームが継続利用しているlive dataだけではなく、起動処理後に回収・decommit可能なGC管理領域であることが分かった。

## GC方式の比較

Production向け方針を決めるため、複数のGC設定を比較した。

### Forced full GC / non-compacting

managed memory自体はAggressive GCと同程度まで回収できたが、Working Setは十分に減らなかった。

### Forced + compacting + LOH CompactOnce

同様にmanaged memoryは減ったが、Working Set削減効果は小さかった。

### Aggressive + compacting

大量口上構成で約1.45 GB級のWorking Set削減を再現した。

### explicit LOH CompactOnce

`Aggressive + compacting` に加えて明示的な `LargeObjectHeapCompactionMode.CompactOnce` を指定してもWorking Set削減や停止時間に実質的な改善がなかったため、Production方針では使用しない。

### Workstation GC

大量口上構成ではWorking Setが約10.5%下がった一方、InputReadyが約129%悪化したため不採用とした。

### Server GC HeapCount 8 / 4

Working Setが逆に増加し、特にHeapCount 4では起動時間も悪化したため不採用とした。

### GCConserveMemory 5 / 7

大量口上構成でWorking Set削減を得られず、起動時間も悪化したため不採用とした。

以上から、通常のServer GC構成は維持し、大規模構成に限定して起動完了時にAggressive GCを1回実行する方針とした。

## 条件付きStartup Memory Trim

毎回Aggressive GCを実行すると小規模構成まで起動時間が増えるため、起動完了時のmanaged memoryを条件にして発動を分ける。

Production方針は次のとおり。

```text
起動完了時 managed memory < 2 GiB
    → Trimを実行しない

起動完了時 managed memory >= 2 GiB
    → Aggressive / blocking / compacting full GCを1回実行
```

判定にはWorking Setではなくmanaged memoryを使用する。GCで整理できないnative/UI側のメモリが大きいだけのケースで、不必要にfull GCを発動しないためである。

### Normal構成

3回すべてで閾値未満となりTrimをskipした。

InputReady中央値は、

- Baseline: 3794.584 ms
- Candidate: 3780.077 ms

で、明確な起動性能退行は確認されなかった。

### 大量口上構成

3回すべてで2 GiB閾値を超え、Trimを実行した。

Working Set中央値:

```text
4,138,422,272
→
2,636,218,368 bytes

-1,502,203,904 bytes
-36.30%
```

Managed memory中央値:

```text

```

InputReady中央値:

Trim処理自体の中央値は約1036 msだった。

したがって、大量口上構成では起動時に約1秒余分に待つ代わりに、起動後のWorking Setを約1.50 GB削減する結果となった。

この値は今回使用した検証fixtureでの結果であり、すべてのゲームで同じ削減量になることを保証するものではない。

## タスクマネージャー上のメモリについて

今回削減している値には2種類ある。

### Total managed allocation

ERB読み込み中に累計で何byteのmanaged objectを確保したかを示す。

CharStream、ReadString、IdentifierWord等の最適化は主にこちらへ効く。

### Working Set

その時点でWindowsがプロセスへ割り当てている物理メモリ量に近く、タスクマネージャーの「メモリ」表示と関係が深い。

条件付きAggressive Trimは主にこちらを大きく減らす目的で導入した。

そのため、起動途中では一時的に大きなメモリ使用量になる場合がある。大量のERBを読み込んだ後、2 GiB閾値を超えていれば起動完了時に整理される。

## 互換性・安全性

今回採用した各変更について、

- Release Build
- Normal Startup
- Kojo Startup
- Parser error
- Lv2 warning
- Exception / Crash
- 対象箇所のfocused semantic

を確認した。

GC方式の変更はERB構文、ゲーム処理、セーブ形式を変更しない。

## 最終方針

今回の更新では、

- パーサーが起動中に作る短命オブジェクトを減らす
- 通常のServer GC設定は維持する
- 小規模構成では余計なfull GCを実行しない
- managed memoryが2 GiB以上の大規模構成だけ起動完了時にAggressive GCを1回実行する

方針を採用した。

目的は「すべての環境で起動を高速化する」ことではなく、大量のERBを扱う場合の無駄なallocationと、起動後に大きく残るWorking Setを抑えることである。

## LoopState Candidate B Production Adoption（2026-08-15）

LoopState Candidate BをProductionへ採用した。通常`InstructionLine`からloop専用の`LoopEnd` / `LoopCounter` / `LoopStep`領域を分離し、FOR / REPEATの開始行だけが`LoopInstructionLine`を使用する。Candidate Aのsidecar方式や新しいdictionary/cacheは含めていない。Normal/Kojo startup、FOR、REPEAT、再入の最小runtime smokeをPASSした。これは高速化または完全同速の断定ではない。

## CharStream Candidate A Production Adoption（2026-08-15）

`EraStreamReader.ReadEnabledLine` 内で、外部へ返す前のローカル `CharStream` を `Reset` して再利用する最適化を採用した。共有pool/cacheは使用していない。Normal/Kojo互換性はPASSで、Startupで明確な性能退行は確認されなかった。

## ReadString Candidate B Production Adoption（2026-08-15）

`LexicalAnalyzer.ReadString` のno-escape fast pathを採用した。escape無し文字列では`StringBuilder`生成を回避し、escape有りでは従来相当の経路へfallbackする。focused compatibility、Normal/Kojo startup PASSを確認した。明確な一貫した性能退行は確認されなかった。

## ReadFirstIdentifier Candidate D Production Adoption（2026-08-15）

行頭命令名解析で、`LogicalLineParser` が`.Code`だけを必要とする経路の一時`IdentifierWord` wrapper生成を除去した。`ReadFirstIdentifierWord` 自体は残し、共有cache・pool・static mutable stateは追加していない。Release build、Normal/Kojo startup compatibilityはPASSした。

## Candidate K Conditional Aggressive Startup Trim Production Adoption（2026-08-15）

起動完了時のmanaged memoryが2GiB未満なら強制GCをskipし、2GiB以上ならAggressive / blocking / compacting full GCを1回実行する条件付き経路をProductionへ採用した。explicit LOH `CompactOnce` は使用しない。通常構成はtrimをskipし、大規模構成では起動後Working Set削減と起動待ち時間のtrade-offを受け入れる方針である。
