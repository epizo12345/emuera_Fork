# 今回の修正説明 — 2026-08-19

## Phase 12B1.1 runtime allocation optimization

### 背景

通常プレイ中にWorking Setが3GB台へ増える問題を調査した。Phase 11のAggressive GC診断では一時的にWorking Setが約3.4GBから約2.65GBへ、managed memoryが約737MiB減少したが、その後再増加した。単純な画像・表示履歴leakではなく、短命allocationとGC heap高水位化が主要因と判断した。

### Phase 12 profiling

startup parser tailを除外したclean gameplay windowでallocation sourceを調査した。通常プレイallocation profileでは、Baselineの`System.Int64[,]`が約112.2MB、`PrivateInt2DVariableToken.ScopeIn`が約90MB（約110秒）だった。B1では`System.Int64[,]`が約8.96MB（120秒）、`PrivateInt2DVariableToken.ScopeIn`のsampled allocationが0だった。

run全体のallocation量はプレイ内容差があるため、採用判断は変更対象type/siteの直接比較を主根拠とした。

### B1

`PrivateInt2DVariableToken`で、top-level配列を再利用するようにした。再利用前には`Array.Clear`を行い、nested / recursive callは従来どおり新規配列を確保する。unbounded poolは作らず、`arrayStack`による外側scope復帰も維持する。

### B1.1

B1では巨大private 2D配列もtokenごとに保持し得るため、正式版では`MaxReusableArrayElements = 32 * 1024`を追加した。32,768 Int64要素はpayload最大256KiBに相当し、上限を超える配列はspareとして保持しない。実ゲームfixtureで確認したprivate dynamic 2D整数配列は38定義、確認できた最大は100 × 200 = 20,000要素だった。

### 効果

- `System.Int64[,]`の対象allocation rateを時間差補正後に約92.7%削減した。
- `PrivateInt2DVariableToken.ScopeIn`のsampled allocationは0になった。
- top-levelで再利用する範囲では短命な巨大配列allocationとGC pressureを減らし、32,768要素上限により巨大配列を無制限にretainedする設計にはしていない。
- これは対象type/siteのallocation効果であり、B1.1単独でWorking Set全体がどれだけ下がるか、起動後のPrivate Bytesがどう変わるかは別測定であり、この記録では確定していない。

### 検証

時間差補正後、対象`System.Int64[,]` allocation rateは約92.7%削減され、`PrivateInt2DVariableToken.ScopeIn`のsampled allocationは0だった。

### 互換性

- ERB/ERH形式変更なし
- セーブ形式変更なし
- 評価順変更なし
- RNG消費順変更なし
- 入力 / WAIT / 中断変更なし
- nested / recursive配列の独立性を維持
- top-level開始時に再利用配列を0クリア

### 採用状態

- Release / win-x64 / framework-dependent / self-contained false
- PublishSingleFile=trueのsmoke済みcandidateを配布へ使用
- `Emuera.exe`: 24,639,210 bytes
- SHA-256: `490A18439767811468D930D8D8E3A69DFEA5DDD7B7D904A65A47B04A8B8DAE33`
- Release 0 errors / 35 warnings
- 既存セーブを含む通常プレイsmoke異常なし

## Phase 12C strict color-only FONT fast path

### 背景と範囲

`HtmlManager.Html2DisplayLine`のHTML解析について、互換性を維持したまま適格な入力だけを短絡する方式を、Phase 12C2/C3/C5で検証した。Productionでは診断用shadow経路や`PerformanceMetrics`を追加せず、対象入力以外は従来のAngleSharp解析へ戻す。

### 実装

- 完全入力を先に走査し、通常文字列と厳密な`<font color = '#RRGGBB'>text</font>`だけを受理する。
- 非FONTタグ、属性追加、nested FONT、entity、大小文字違い、引用符違い、named color、制御文字などはfast pathで受理せず、従来のAngleSharpへfallbackする。
- 受理後は既存の`ConsoleStyledString`、`ConsoleButtonString`、`PrintStringBuffer.ButtonsToDisplayLines`を使用し、表示オブジェクトの構築規則を共用する。

### 効果

従来は対象文字列でもAngleSharpの汎用HTML parseを通していたため、対象外HTMLとの互換性には強い一方、strict color-only FONTだけを処理する経路としては重いallocationと解析処理が発生していた。完全入力を先に判定し、対象だけを既存表示オブジェクトへ短絡することで、同値性を保ったまま対象経路のコストを削減した。

- same-input測定でsteady allocationはAngleSharp `117,515,072 bytes`からfast path `22,517,512 bytes`へ減少し、対象経路の削減量は`94,997,560 bytes`（約80.839%）だった。
- 対象経路の処理時間は約87.346%削減した。
- これらはstrict color-only FONT対象経路の実測値であり、ゲーム全体のallocationや起動時間が80%/87%改善したことを意味しない。非対象入力は従来のAngleSharpへfallbackするため、全HTMLを短絡する変更ではない。

### 検証

- C2 v2: 適格入力7,938件、既存経路との同値7,938/7,938、mismatch 0、例外0。
- C3: formal single-file smokeでprocess exit code 0。Kojo起動はInit 3969ms、ERB 2625ms、Lv2=0。
- C5 same-input: 適格入力5,538/5,538、mismatch 0。steady allocationはAngleSharp 117,515,072 bytesに対しfast path 22,517,512 bytesで、対象経路の削減量94,997,560 bytes（約80.839%）、時間は約87.346%削減。順序入替えでも同傾向を確認した。
- 上記削減率はstrict color-only FONT対象経路限定であり、ゲーム全体のallocation削減率を示すものではない。
- Release buildは0 errors / 35 warnings、新規warning 0。通常配布EXEは24,643,306 bytes、SHA-256は`4CE75612E0A370DC6FFDD80F369E0E50F9F31F0CD81AA732F35F4FDBBFD6B271`。

### 採用状態

Phase 12Cとして正式採用し、strict対象だけをfast path、それ以外を従来解析へfallbackする方針を正式配布版へ反映した。
