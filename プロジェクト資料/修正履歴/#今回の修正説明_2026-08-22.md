# 今回の修正説明（2026-08-22）

## Phase 13R32 LogicalLine error-state slot compaction

### 背景

`LogicalLine`は全instanceで`bool isError`と`string errMes`を別々に保持していたが、productionのerror経路では正常行のfalse/空文字、error行のtrue/メッセージという対応だけが使われ、`IsError=false`と非empty`ErrMes`、または`IsError=true`とnull`ErrMes`を長期保持する経路はなかった。独立したbool fieldを全`LogicalLine` instanceが保持しており、object layout / alignmentを含めて大量retained時のshallow sizeを押し上げていた。

### 実装

`Runtime/Script/Statements/LogicalLine.cs`で`isError`を削除し、`errMes`のnullを正常、空文字をメッセージなしerror、非emptyをメッセージ付きerrorとして扱うよう統合した。`ErrMes`は正常行で従来どおり空文字を返し、`IsError=true` setterは既存の「flag→message」設定順を受けるため空文字sentinelを作る。`InvalidLine` / `InvalidLabelLine`の常時error、lazy argument parser、ParserMediator.Warn、ArgumentBuilder、CALL先error伝播の意味論は変更していない。

### 効果

- R32単独（R31 → R32）の候補heap census実測: `InstructionLine` `3,902,466 objects`、shallow `104 → 96 bytes`、`405,856,464 → 374,636,736 bytes`、差分`-31,219,728 bytes`（約29.77 MiB）。
- `InstructionLine` object countは変化せず、独立した`isError` fieldを削除した結果、`InstructionLine`のobject layoutがinstanceあたり8 bytes縮小した型別効果である。
- managed live総量はR32候補censusで`1,991,781,642 bytes / 31,539,294 objects`を取得した。R31記録とはheap取得時点・状態が揃わないため、R32単独のmanaged live差分は未確定とする。
- Task Manager上のPrivate Bytes、startup/runtime速度の改善量は未測定。正常行が大量にretainedされる大規模ERBほど、全instanceに効く8 bytes削減の効果が大きい。

### 検証

- whole-repo static audit: `IsError=false`、`ErrMes=null`のproduction設定、reflection/serialization対象、長期独立error state、再利用のためのerror解除経路なし。`InvalidLine` / `InvalidLabelLine` override、ParserMediator.Warn、ArgumentBuilder、lazy ArgumentParser、CALL error伝播を確認。
- focused state: normal line、`IsError=true`、message設定、clear、ParserMediator.Warn、InvalidLine、InvalidLabelLine、field型とfield削除を確認。
- lazy error guard: error message保持後のArgumentParser再呼出しでerror状態と`CodeEE` messageを保持。
- Release build: 0 errors / 35 existing warnings / new warning 0。
- candidate startup: 3/3 PASS、平均Init 4,070.3ms、平均ERB 2,578ms、Lv2 warning 0。
- formal fixture smoke: InputReady後にsave219をロードし、ロード後のゲーム画面から`(H\e\nd\e\n)*100`（400入力ステップ）を実行。macro完了後もゲーム画面を維持、process異常終了なし、Lv2 warning 0。1回PASS（11,884.3ms）。
- EVENT_93 static impact: LOADGLOBAL / SAVEGLOBAL、ARRAYSHIFT、CALLFORM、 大場ななの記憶、キャラ再構成を含むERBを確認。error metadata layoutだけを変更し、これらの意味論とsave formatには直接触れていない。

### 採用状態

Phase 13R32として正式採用した。`LogicalLine`のerror flagとmessageを1参照slotへ統合し、lazy parse互換、InvalidLine semantics、CALL error伝播を維持した。

正式配布EXE: 24,643,306 bytes

SHA-256: `1B1D3A826590D7AF5D1E65658F7AA1911C15D2BB7003ED650DB99E98497B4C24`

## Phase 13R31 LogicalLine ScriptPosition nullable storage compaction

### 背景

`LogicalLine`は位置情報を公開上`ScriptPosition? Position`として扱う一方、内部では全行がnullable fieldを保持していた。位置なし行にもnullable管理用の参照領域が必要になり、大量にretainedされる`LogicalLine`/`InstructionLine`では、実際の位置情報の有無に関係なくオブジェクトshallow sizeを押し上げる要因になっていた。

`ScriptPosition`の通常生成時は`Filename`がnullにならず、位置なしを表す既存のnullable状態と、明示的な`new ScriptPosition()`（`Filename=""`、`LineNo=-1`）も区別できるため、内部だけsentinelへ置き換えた。

### 実装

`Runtime/Script/Statements/LogicalLine.cs`の内部fieldだけを`ScriptPosition?`から非nullableの`ScriptPosition`へ変更し、`default(ScriptPosition)`（`Filename == null`）を位置なしsentinelとして使用した。公開`Position` getterはsentinelを従来の`null`へ変換し、constructor、`ToString()`、label ordering、reload/error経路の外向き挙動は維持した。`ScriptPosition` struct、`EmueraException`、save format、ERB解析順、GC policyは変更していない。

### 効果

- 候補版heap census実測: `InstructionLine` `3,902,466 objects`、shallow `112 → 104 bytes`、`437,076,192 → 405,856,464 bytes`、差分`-31,219,728 bytes`（約29.77 MiB）。
- これはR31の`LogicalLine`内部slot削減による型別実測値であり、object countは変化していない。
- managed live総量は候補censusで`2,064,573,606 bytes / 32,025,609 objects`を取得したが、R30記録の基準とは取得タイミング・heap状態が揃わないため、R31単独の総量差分としては扱わない。
- Task Manager上のPrivate Bytes、startup/runtime速度の改善量は未測定。`LogicalLine` / `InstructionLine`が大量にretainedされる構成ほど、instanceあたり8 bytesの削減が全体のretained memoryへ大きく効く。

### 検証

- static audit: `default(ScriptPosition)` sentinelと通常の`new ScriptPosition(string, int)`、明示的`new ScriptPosition()`の衝突なし。`Position` nullable API、label ordering、reload removal、error position経路を確認。
- Release build: 0 errors / 35 existing warnings / new warning 0。
- focused semantic: 位置なし行、明示的default位置、通常位置、label ordering、error position、reload removalを確認。
- fixture smoke: formal EXEでInputReady到達後に既存標準手順で`save219.sav`をロードし、ロード後のゲーム画面から`(H\e\nd\e\n)*100`（入力ステップ400）を実行。ロード後・macro完了後ともゲーム画面を維持し、CSV完了記録、process異常終了なし、Lv2 warning増加なし。startup 3/3 PASS（平均Init 3,859.3ms、平均ERB 2,340.3ms）、正しいsave219後macroは1回PASS（完了推定16,522.1ms）。
- EVENT_93 fixtureのLOADGLOBAL/SAVEGLOBAL、CALLFORM、ARRAYSHIFT等は既存parser/label経路で確認し、R31変更による直接の意味論変更なし。

### 採用状態

Phase 13R31として正式採用した。内部専用のnullable位置slotを削除し、公開nullable semanticsとsave互換性を維持したままInstructionLine retained sizeを削減した。

正式配布EXE: 24,643,306 bytes

SHA-256: `93F184794420DAD826AC7CECF58AE265D575973D42C4D930B3CE882BF0427950`

## Phase 13R30 InstructionLine assignment-destination slot compaction

### 背景とstatic audit

R29 retained censusで`InstructionLine`は`3,902,466 objects / 468,295,920 bytes`（shallow 120 bytes）を占めていた。`assigndest`はSET左辺を遅延引数解析まで保持する専用参照だったため、既存の`auxiliaryData` unionへ移す候補とした。

- `assigndest`はSET assignment constructorと`PopAssignmentDestStr()`だけで使用されていた。
- `IfCaseList`、`dataList`、`callList`、`JumpToEndCatch`は別FunctionCodeのloader/runtime経路で、SETと共存しないことを再確認した。
- `SP_SET_ArgumentBuilder.CreateArgument()`は左辺をpopしてから従来どおりRHS `CharStream`をpopするため、左辺→右辺の解析順とlazy parsingを維持できる。

### 実装

`Runtime/Script/Statements/LogicalLine.cs`だけを変更した。assignment constructorは左辺`WordCollection`を`auxiliaryData`へ格納し、`PopAssignmentDestStr()`は同slotから取得して直ちにnull化する。`argumentStorage`、`JumpTo`、`ParentLabelLine`、save format、GC設定は変更していない。wrapper / tuple / pair objectは追加していない。

### 効果

- `InstructionLine`: `468,295,920 → 437,076,192 bytes`
- object count: `3,902,466 → 3,902,466`
- shallow size: `120 → 112 bytes`
- `SingleLongTerm`、`VariableTerm`、`FunctionMethodTerm`等の主要型は大きな増加なし

専用参照slotを全`InstructionLine`へ持たせないことで、同じobject数でも各instanceのshallow sizeを8 bytes削減した。特に`InstructionLine`が大量にretainedされるfixtureで効果が大きく、managed live heap全体でも削減を確認した。Task Manager上のPrivate Bytesが同量下がることやruntime速度向上は、この測定からは保証しない。

managed live heapの比較は、R30単独とR29+R30累積を分けて扱う。

- R30単独（R29 → R30）: `2,009,815,855 → 1,979,922,869 bytes`、既存測定値からの差分は`-29,892,986 bytes`（約28.5 MiB）。
- R29 + R30累積（R28 → R30）: `2,073,037,181 → 1,979,922,869 bytes`、差分は`-93,114,312 bytes / -1,910,410 objects`。

後者はR29のparsed AST小整数共有とR30のInstructionLine slot削減を合わせた累積値であり、R30単独の削減量ではない。

focused semanticは、通常SET、配列/添字、RHS式、lazy argument parsing、文字列代入を含む既存parser/runtime経路のsource確認と実ゲームmacroで確認した。評価順、error state、jump、auxiliaryData利用命令の挙動に変更はない。

### 検証

- Release build: 0 errors / 35 existing warnings / new warning 0
- candidate smoke: InputReady PASS、save219 PASS、RepeatCount=100 PASS（12,530ms）
- formal EXE smoke: InputReady PASS、save219 PASS、RepeatCount=100 PASS（11,692ms）、Lv2 warning 0
- startup regression: 単発測定のため明白な悪化なし、統計的な比較は未測定

### 採用状態

Phase 13R30として正式採用した。専用`assigndest` fieldを削除し、InstructionLineのretained shallow sizeを8 bytes削減した。

正式配布EXE: 24,643,306 bytes

SHA-256: `983713FB3FBB1E805291DAA11EFC9D17FE5F5600518803F6D7E3DD15407B6673`

## Phase 13R29 Parsed AST small-integer canonicalization

### 背景

pre-R29のR28正式EXEでは、Title / InputReady / Init:End後のmanaged live heapが`2,073,037,181 bytes / 39,354,018 objects`で、`SingleLongTerm`は`83,040,896 bytes / 2,595,028 objects`を保持していた。ERB integer literalのparser経路が、R25の既存cacheを使わず毎回`new SingleLongTerm(i)`していたため、parsed ASTのretained footprint削減候補とした。

### Static audit

- `SingleLongTerm`はconstructor後に変更されない`readonly iValue`を持ち、`GetValue()`と`Restructure()`は従来どおり`this`を返す。
- instance identityを意味論として使うproduction経路、`Dictionary` / `HashSet` key利用、reflection、field mutationは見つからなかった。
- source positionなどの状態を`SingleLongTerm`へ保持していないため、immutable cache共有は安全と判断した。

### 実装

`Runtime/Script/Statements/Expression/ExpressionParser.cs`の`TermStack.Add(long)`だけを、`new SingleLongTerm(i)`から`SingleLongTerm.FromValue(i)`へ変更した。R25のcache範囲`-1..255`は維持し、範囲外は従来どおり個別instanceを生成する。InstructionLine、save format、評価順、GC policyは変更していない。

### 効果

- baseline managed live: `2,073,037,181 bytes / 39,354,018 objects`
- patched managed live: `2,009,815,855 bytes / 37,383,690 objects`
- managed live delta: `-63,221,326 bytes / -1,970,328 objects`
- baseline `SingleLongTerm`: `2,595,028 objects / 83,040,896 bytes`
- patched `SingleLongTerm`: `595,821 objects / 19,066,272 bytes`
- `SingleLongTerm` delta: `-1,999,207 objects / -63,974,624 bytes`（約`-77.04%`）
- `InstructionLine`は`468,295,920 bytes`で変化なし。主要な式・配列型も差分は数百bytes以内だった。

R25で作った-1〜255のimmutable cacheをparsed ASTのinteger literal経路にも適用したことで、同じ小整数literalごとの`SingleLongTerm` retained instanceを共有できるようになった。今回のfixtureではmanaged liveを約63.2MB、`SingleLongTerm`を約64.0MB削減した。これはparsed ASTを多く保持する条件での実測であり、全ゲーム・Working Set・runtime速度へ同じ削減量が出るとは限らない。

### 検証
- reflectionによる境界値確認で、`-1, 0, 1, 255`は同一instance、`256, -2`および大整数は非共有、値は全て一致した。
- unary / binary / ternary、variable index、function argument、CASE、CONST / restructureの既存parser・評価経路は変更せず、実ゲームsmokeで回帰なしを確認した。

### Build / smoke

- Release build: 0 errors / 35 existing warnings / new warning 0
- 口上有りfixture: InputReady PASS、save219 PASS、RepeatCount=100 PASS（process-wide driver観測17,335ms）
- startup smoke: Init:End / InputReady PASS、Lv2 warning 0
- startup regression: 単発条件差があるため信頼できる比較は未測定

### 採用状態

Phase 13R29として正式採用した。小整数literalだけを既存immutable cacheへcanonicalizeし、cache外の値、評価順、save互換性を変更しない。次候補はInstructionLine retained layout compactionとする。

正式配布EXE: 24,643,306 bytes

SHA-256: `948D71D0FCAE66B623A298A0EC924379A441F7230D6A6BFA294EFA24BD46B04F`

## Phase 13R28 SingleStrTerm empty-value sharing

### 背景

runtimeの文字列値返却で、空文字列`""`の`SingleStrTerm` wrapperが短命に繰り返し生成されていた。空文字の頻度とゲーム全体のplateau削減量は未測定のため、今回の採用根拠は空文字wrapper allocationのsource上の除去、semantics維持、focused確認、Release build、実ゲームsmokeとした。

空文字は値としては同一でも、従来は返却のたびに別wrapperを作っていたため、空文字を多く返すruntime経路では短命allocationとGen0/GC workが積み上がっていた。一方、任意文字列まで共有すると保持量や文字列identityの影響範囲が広がるため、対象を空文字だけに限定した。

### Static audit

- `SingleStrTerm`生成箇所、`.Str`、`is SingleStrTerm`、`ReferenceEquals`、reflection、`sValue`書換えをwhole-repo検索した。
- constructor後に内部文字列を書き換えるproduction経路はなく、`GetValue()`は従来どおり`this`を返す。
- `SingleStrTerm` instance identityを意味論として使うproduction経路はなく、共有によりERB semanticsは変わらない。
- `sValue`を`readonly`化した。`null`と空文字の意味は混同していない。

### 実装

`Runtime/Script/Statements/Expression/Term.cs`に空文字専用の`EmptyTerm`と`FromValue` factoryを追加した。`value != null && value.Length == 0`のときだけ共有し、`null`と非empty文字列は従来どおり個別instanceを生成する。Dictionary cache、任意文字列cache、string interning、poolingは採用していない。

runtime/value-wrapper経路として、`VariableTerm.GetValue`、`FunctionMethod.GetReturnValue`、UDF string fallback、`AExpression.GetValue`、`StrFormTerm`、formatted string function returnをfactoryへ移行した。parser/config/static ASTの直接constructorは広い一括置換を避けて維持した。

### 効果

空文字の`SingleStrTerm` wrapperを1個へ共有し、対象経路の短命allocation、Gen0 pressure、GC work、runtime churnを削減する。空文字頻度に応じて効果量は変わり、ゲーム全体のWorking SetやTask Manager plateauが直接大幅低下すること、runtime速度が改善することは未測定である。

### 検証

Release DLLをreflectionで直接確認し、次をPASSとした。

- `FromValue("")` / `FromValue(string.Empty)`の同一instance共有
- 非empty値の正しさと独立instance
- `FromValue(null)`がempty singletonへ畳み込まれず、null同士も共有しないこと
- `.Str`、`GetValue()`、`ToString()`、`sValue readonly`
- nullの`ToString()`例外が従来どおりであること

### Build / smoke

- Release build: 0 errors / 35 existing warnings / new warning 0
- formal publish: Release / win-x64 / framework-dependent / self-contained false / PublishSingleFile true / EnablePerformanceMetrics false
- 口上有りfixtureでInputReady PASS、save219 PASS、`(H\\e\\nd\\e\\n)*100`のRepeatCount=100 smoke PASS（観測7,474ms）
- 既存macro harnessはsave画面で`Process.MainWindowHandle`だけを検索するためtimeoutした。process-wideのtop-level window検索による同等driverで検証を完了し、アプリ終了・例外はなかった。

### 採用状態

Phase 13R28として正式採用した。主効果は`SingleStrTerm`の空文字短命allocation、Gen0 pressure、GC work、runtime churnの削減可能性であり、空文字頻度に応じて効果量は変わる。任意文字列を保持しないため、cache自身による有意なretained memory増加は避けている。ゲーム全体のWorking SetやTask Manager plateauが直接大幅低下すると主張しない。

正式配布EXE: 24,643,306 bytes

SHA-256: `DBECAA7077624A3C0EB70527C5580F6DB8CBE53368432ABCE8F009EAAE5A8F6F`
