# 今回の修正説明（2026-08-21）

## Phase 13R14 TermStack storage最適化

### 背景

Phase 13R10〜R13で、ERB式解析時のTermStackについて、単一要素のために都度`Stack<object>`を確保している経路を確認した。R13ではServer GC / Workstation GCの双方で、同一条件の反復検証と通常・口上有りfixtureの回帰確認を実施した。

単一要素しかない式でも空の`Stack<object>`本体と内部領域を作ってすぐ捨てていたため、式解析のhot pathで短命objectと配列のallocationが積み上がり、GCへ渡す仕事を増やしていた。大量のERB・口上を起動時に解析する構成ほどこの無駄が大きく、速度改善だけでなくmanaged allocation削減を修正対象にした。

### 実装

`Runtime/Script/Statements/Expression/ExpressionParser.cs`のTermStackを、空状態・単一要素のinline storage・複数要素時の`Stack<object>`昇格で保持する形へ変更した。式の評価順、演算子処理、セーブ形式、GCポリシーは変更していない。Workstation GCの採用やGC設定変更も行っていない。

### 効果

- ScriptParse中の一時allocationをServerで251,430,450 bytes（9.60%）、Workstationで251,445,633 bytes（9.60%）削減した。
- 主な効果は単一要素式での`Stack<object>`本体・内部配列の短命allocationと、それに伴うGC workの削減である。
- 起動後のretained/live memory、Working Set、プレイ中runtime allocationの削減量はこのPhaseでは未測定であり、ScriptParse allocation値から推測しない。
- 起動速度は複数回測定で明確な改善を確定できず、速度効果は未証明とした。

### 検証

- Server / Workstation各10回、合計40回の有効な反復を実施。
- Normal / 口上有りfixtureでInputReady到達、Lv2 warning 0。
- 起動速度について明確な回帰は確認されず、R13の判定はPASS。ただし高速化とは断定していない。
- Release build、正式single-file publish、Normal / Kojo smokeを完了。

上記allocation値はScriptParse中の一時allocationについての測定であり、常駐Working Setやプレイ中のメモリplateau削減を意味しない。次の調査対象はretained/live/committed memoryの実測とする。

### 採用状態

Phase 13R14として正式採用し、正式配布版へ反映した。

## Phase 13R22 VariableToken.CheckElement共有mask最適化

### 背景

引数省略版の`CheckElement`は、判定内容が常に`[true, true, true]`であるにもかかわらず、hot pathで毎回3要素のbool配列を生成していた。配列は判定後に保持されないため、呼出し回数に比例した短命allocationとGC pressureだけが発生していた。

### 実装

`[true, true, true]`を`static readonly`共有maskへ変更した。overrideはmaskをread-only参照するため、判定挙動と呼出し側の契約は維持した。

### 効果

引数省略版ではbool配列の新規allocationを呼出しごとに行わなくなり、短命object/配列とそれに伴うGC workを削減する。対象経路の実測byte数、ゲーム全体のallocation、startup/runtime速度、retained memoryは既存記録では未測定である。

### 検証

Release 0 errors / 35 existing warnings、save219ロード、RepeatCount=100 macro smoke PASS。

### 採用状態

正式single-fileへ反映した。EXE 24,643,306 bytes、SHA-256は既存記録の`C3DE...2A73`。

## Phase 13R23 PrivateInt1D bounded reuse

### 背景

private dynamic 1D整数配列のtop-level呼出しでは、同じサイズの配列を毎回確保していました。既存の2D bounded reuseと同じく、保持量に上限を設けた再利用が可能です。

### 実装

`Runtime/Script/Statements/Variable/VariableToken.cs`の`PrivateInt1DVariableToken`に、最大32,768要素（256 KiB）までのspare配列を1個だけ保持するbounded reuseを追加しました。再利用前に`Array.Clear`し、default値がある場合は復元します。nested / recursive呼出しでは従来どおり新規配列を使って外側の値を保持し、32,768要素を超える配列は保持しません。

### 効果

同じサイズのtop-level呼出しで配列を毎回確保せずに済むため、短命な`Int64[]` allocationとGC pressureを減らす。再利用を32,768要素・1個に制限したため、巨大配列をretainedさせ続ける無制限poolにはならない。対象経路の削減byte数、startup/runtime速度、Working Setの変化は既存記録では未測定である。

### 検証

- Release build 0 errors / 35 existing warnings / Candidate由来new warning 0。
- default値なしの再利用clear、default値復元、nested / recursive外側値復元、32,768要素境界をRelease DLLの最小focused確認でPASS。
- 既存fixtureでsave219ロード後のRepeatCount=100 macro smokeを完了。

### 採用状態

Phase 13R23として正式採用し、正式single-file配布版へ反映した。配布EXEは24,643,306 bytes、SHA-256は`F7E145FB01E574A94C27221BE3B370EACFB3A130B7B60BD220A93B18BC034191`。

## Phase 13R24 FixedVariableTerm lease化

### 背景

短時間だけ使用する`FixedVariableTerm`について、残っていた`GetFixedVariableTerm` callerでは毎回termと内部添字配列を確保していました。既存の`RentFixedVariableTerm` / `FixedVariableTermLease` pool経路を安全なmethod-local callerへ広げました。

### 実装

`Runtime/Script/Process.ScriptProc.cs`のSWAP、ARRAYSHIFT、ARRAYREMOVE、ARRAYSORTと、`Runtime/Script/Statements/Function/Creator.Method.cs`の10 callerをlease化しました。SWAPでは2個のleaseを同時に保持し、従来のvar1→var2添字確定順を維持しています。leaseの`Term`はfieldやreturn値へ出さず、using scope内だけで使用します。`GetFixedVariableTerm`本体、pool設計、FixedVariableTerm内部構造は変更していません。

### 効果

method-localで短時間しか使わないtermと内部添字配列をleaseから再利用できるため、対象callerでの短命allocationとGC workを削減する。field保存やreturnを伴うcallerには広げていないため、leaseの寿命を越えた参照を残さない。対象経路の削減byte数、startup/runtime速度、retained memoryは既存記録では未測定である。

### 検証

- 全10 callerをA（method-local短命利用）として監査し、field保存・return・遅延利用はありませんでした。定義2件はKEEP。
- SWAP、動的添字、ARRAYSHIFT / ARRAYREMOVE / ARRAYSORT、MAXARRAY / FINDELEMENT / INRANGEARRAY / STRJOINの既存fixture経路を含むsave219 smokeを確認しました。連続macroでもlease返却後の次回添字漏れはありませんでした。
- Release build 0 errors / 35 existing warnings / R24由来new warning 0。
- 既存fixtureでInputReady、save219ロード、RepeatCount=100 macro smokeを完了。

### 採用状態

Phase 13R24として正式採用し、正式single-file配布版へ反映した。配布EXEは24,643,306 bytes、SHA-256は`001E0E4E6DB4C0D42EB56294194474A3BF017B38115EC4707FCA0A70CDB4B31D`。

## Phase 13R25 SingleLongTerm小整数共有

### 背景

runtimeの整数値返却経路では、同じ小整数を表す`SingleLongTerm`を値返却のたびに個別生成していた。値が同じでも各wrapperは短命で、頻出する小整数ほどallocationとGC workが積み上がるため、値を変更できない範囲だけ共有対象にした。

### 実装

`SingleLongTerm`に-1〜255の257個のimmutable固定cacheと`FromValue` factoryを追加し、`VariableTerm.GetValue`と`FunctionMethod.GetReturnValue`（および整数のnull fallback）で使用した。cache外の値は従来どおり新規instanceを生成し、整数の意味論・評価順は変更していない。

### 効果

- -1〜255の頻出整数ではwrapperの新規allocationを避け、短命objectとGC pressureを削減する。
- cacheは257個の固定instanceだけで、任意の整数を保持するcacheではないため、cache自身のretained memory増加を限定した。
- Phase 13R25単独のmanaged live、総allocation、速度効果はこの記録では未測定。後続R29ではparsed AST経路への適用効果を別測定した。

### 検証

- identity / mutability監査、cache境界（-1、0、1、255、-2、256）、cached / non-cached値のfocused確認をPASS。
- Release build 0 errors / 35 existing warnings。
- 口上有りfixtureでInputReady到達、Lv2 warning 0のstartup smokeをPASS。

### 採用状態

Phase 13R25として正式採用し、正式single-file配布版へ反映した。

## Phase 13R26 Failed CalledFunction allocation削減

### 背景

TRY系のmissing function / event探索では、対象が存在しない場合に結果を捨てる`CalledFunction`を先に生成していました。

missing targetは呼出しへ進まないため、成功判定前の`CalledFunction`は必ず不要になる。TRY系探索を繰り返す経路では、この短命object生成と破棄がlookup失敗回数に比例して発生し、GC pressureを増やしていた。

### 実装

`Runtime/Script/Process.CalledFunction.cs`でラベルlookupと成功判定を先に行い、対象が存在する場合だけ`CalledFunction`を生成するよう変更しました。成功時のfield設定、event group/counter、通常CALLとevent CALLのエラー semanticsは維持しています。

### 効果

missing function / event経路では`CalledFunction`を生成しなくなるため、失敗探索時の短命allocationとGC workを削減する。成功するCALL経路のallocationを削る変更ではなく、対象がない場合に効果が限定される。削減byte数、startup/runtime速度、retained memoryは既存記録では未測定である。

### 検証

- constructor / lookup safety監査、missing target、successful call/event経路を確認。
- Release build 0 errors / 35 existing warnings。
- 口上有りfixtureでInputReady、save219ロード、RepeatCount=100 macro smokeを確認。

### 採用状態

## Phase 13R27 UserDefinedFunctionArgument selective transporter allocation

### 背景

ユーザー定義関数の引数受け渡しで、実際には使わない型カテゴリのtransporter配列と`isRef` bool配列まで毎回確保していました。

destination signatureが整数だけ、文字列だけ、またはREFなしでも全カテゴリを用意していたため、引数の型構成に関係なく未使用配列と判定用bool配列のallocationが発生していた。UDF呼出し回数と引数数が多い経路ほど、これらの短命配列がGC workを増やしていた。

### 実装

`UserDefinedFunctionArgument`がdestination signatureを一度走査し、整数・文字列・REFで必要な配列だけを`Arguments.Length`で確保するよう変更しました。REF判定は保持したdestination metadataから行い、`isRef`配列を削除しました。CALL、REF、default、変換、再帰の意味論は変更していません。

### 効果

使わない型カテゴリのtransporter配列と`isRef`配列を作らなくなるため、UDFのsignatureが限定的な呼出しほど短命allocationとGC pressureを削減する。必要な配列の容量は従来どおり引数数に合わせ、CALL/REF/default/変換/再帰の状態は保持する。対象経路の削減byte数、startup/runtime速度、retained memoryは既存記録では未測定である。

### 検証

- destination metadata lifetime / transporter参照監査をPASS。
- Release build 0 errors / 35 existing warnings。
- 口上有りfixtureでInputReady、save219ロード、RepeatCount=100 macro smokeを確認。

### 採用状態
