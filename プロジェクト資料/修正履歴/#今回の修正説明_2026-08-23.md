# 今回の修正説明（2026-08-23）

## Phase 13R39 口上まとめ限定 Lazy ERB Hydration

### 背景

実ゲームの口上まとめには488 ERB、約424万物理行があり、従来は通常起動時に口上本文を全てInstructionLine／Argument／ASTへ解析して保持していた。口上なしfixtureとの比較で起動時Managed heapに非常に大きな差があり、初回起動時点ではまだ実行しない口上本文の解析・retentionが主な負荷になっていた。

通常ERB全体をLazy化すると互換性・診断範囲が広がるため、影響が集中している`Data\ERB\口上\口上まとめ\`配下だけを対象にした。キャラ番号やファイル名規則をruntimeへ埋め込まず、関数が実際に実行される直前をhydration triggerとした。

### 実装

- 正規化した相対pathが口上まとめ配下のファイルだけをLazy対象とし、通常ERBは従来どおりeager parseする。
- 起動時は既存parserを使ってFunctionLabelLine、引数metadata、ScriptPosition、FileIndex、`#DIM`／`#DIMS`／`#LOCALSIZE`／`#LOCALSSIZE`、`$` GotoLabelLineなどをindexする。本文のInstructionLine／Argument／ASTは作らない。
- `#FUNCTION`／`#FUNCTIONS`、System/Event、`#PRI`／`#LATER`／`#ONLY`／`#SINGLE`などの危険構造を含むファイルはeager fallbackとした。実fixtureではLazy 478ファイル、fallback 10ファイルとなった。
- `ProcessState.IntoFunction`の引数評価・ScopeIn・functionList追加より前に、未ロード関数の所属ERBをファイル単位でhydrateする。一度Loadedになったファイルは終了まで保持する。
- 起動時に登録したFunctionLabelLine／GotoLabelLineを置換せず、そのidentityを維持したまま本文chainを接続する。`#DIM`等のmetadataも起動時登録し、private variableの初回実行待ち化は行わない。
- hydration時はPreload cacheに依存せず、現在のERBを直接openする。index時のLength／LastWriteTimeUtcと照合し、変更検出時は通常のエラー処理へ倒す。
- AnalysisModeとDebugModeはeager、Preload全体、save format、GC policy、通常LogicalLine／InstructionLineへのper-object field追加は変更していない。
- Trial専用の`phase13r39-lazy-kojo.log`ファイル出力とLoaded／Failed診断writerは正式版から除去した。Unloaded／Loading／Loaded／Failed状態、hydration失敗処理、eager fallback、変更検出は維持した。

### 効果

Trialで開始mainと同じ条件のA/Bを取得した。以下は起動時の実測値であり、新しい推測値ではない。

- KOJO startup Managed: `1,762,740,872 → 1,174,959,288 bytes`
- 差分: `-587,781,584 bytes`（`-33.34%`）
- KOJO startup Working Set: `2,287,828,992 → 2,181,083,136 bytes`
- Lazy本文を起動時に生成しないことで、実行前のInstructionLine／Argument／AST retentionと起動時allocationを抑えた。削減量はゲーム構成・GC状態に依存し、全ゲームのWorking Setが同じ量だけ下がることを意味しない。
- 実機観測では通常起動約1.9GB前後、プラナを含むRepeatCount=1000実行時一時約2.2GB前後、その後約2.0GBまたは約1.9GB付近、口上持ちキャラ約10人使用後も約2.1GB前後で推移した。これはTask Managerによる参考観測であり、heap censusと同一の厳密benchmark値ではない。
- RepeatCount=1000はbaseline `58,546.473ms`、Trial `58,201.072ms`で、明確なmacro速度退行は確認しなかった。初回hydrationを含むruntime速度が常に改善することを主張するものではない。

### 検証

- Trial自動検証でLazy 478、eager fallback 10、startup hydration 0を確認した。
- `$`ラベルを含むLazy ERB、`#DIM`／`#DIMS`を含むLazy ERBのhydrationを確認した。
- save219をロードしてからRepeatCount=100を実行し、入力dispatch、ゲーム進行、応答性、process正常終了、hydration failureなしを確認した。

- 実機で大型口上のラタトスクを調教で使用し、口上持ちキャラ約10人、複数キャラ抽選、調教反復、セーブ→終了→再起動→ロードを確認した。初回hydrationによる体感可能な引っ掛かり、Failed／Errorは確認しなかった。
- DebugModeはeager fallback設計どおり約2.3GB前後であり想定内だった。
- Trial最終差分から診断ログ出力を除去後、Release 0 errors／35 existing warnings／new warning 0、KOJOあり／なし起動、save219＋RepeatCount=100を再確認した。KOJOありのmetrics buildはdispatch 201、`killed=false`、`Responding=True`、displayLineCount 5000、KOJOなしもdispatch 201、`killed=false`、`Responding=True`だった。正式配布EXE自身でもsave219＋RepeatCount=100（7,294.419ms、`Responding=True`）を確認し、`phase13r39-lazy-kojo.log`は生成されなかった。

## Phase 13R39.1 Lazy KOJO ERB 部分再読込の安全化

### 背景

R39の起動時full loaderは、未hydrateの口上関数stubとLazy対応表を保持している。R39.1以前は、口上まとめと無関係なERBを部分・フォルダ再読込した場合にも新しい`ErbLoader`を`Process.erbLoader`へ代入していたため、`LabelDictionary`に残るstubとLazy管理表の所有者が分離し、その関数を後から初めて呼ぶ経路でhydrateできない危険があった。また、口上まとめ配下をpartial reloadすると、stub identity、metadata、Lazy/eager判定、`LabelDictionary`を一体で再構築できなかった。preprocessor行もLazy安全判定に明示されておらず、ファイル全体の有効性を変える構造を遅延対象にする余地が残っていた。

### 実装

- `ReloadPartialErb`と`ReloadErbFolder`は、口上まとめ外だけを対象とする場合にlocal `ErbLoader`で読み直し、activeな`Process.erbLoader`を置換しないようにした。
- 選択ファイルまたは`SearchSubdirectory`の意味を維持した実フォルダ列挙結果に、`Program.ErbDir`基準の正規化pathで口上まとめ配下が1つでも含まれる場合は、partial処理前に`ReloadErbAll`へ昇格する。ERB外部pathはLazy対象外のままとした。
- DebugMode / AnalysisModeではLazy自体が無効なため、口上まとめ対象でもこのfull reload昇格を行わず、従来のpartial/folder reloadを維持する。
- Lazy安全判定で、先頭の有効文字が`[`で次が`[`ではないpreprocessor行をeager fallbackとした。`[[...]]`のrename表記はfallbackさせない。
- R39のLazy対象範囲、hydration trigger、identity、save format、GC policy、Preload全体、通常ERBのeager処理は変更していない。

### 効果

これは性能改善ではなく、部分再読込後も未hydrate Lazy口上を初回実行時に正しいactive managerからhydrateできるようにする互換性・安全性修正である。部分再読込で無関係なERBを扱ってもLazy管理表が失われず、口上まとめを対象にした場合はfull reloadでstubとmetadataを一体再構築する。新しいmemory削減量・速度向上は主張していない。

### 検証

- Release buildは0 errors、35 existing warnings、new warning 0。初回に追加されたCA1865は修正後の再buildで消滅した。
- KOJOありfixtureで`Lazy 478 / fallback 10`、`Proc:Init:ERB:End`、`InputReady`到達を確認し、startup hydration 0を維持した。KOJOなしfixtureは`Lazy 0 / fallback 0`で正常起動した。
- 候補EXEでsave219をロードしてから`(H\e\nd\e\n)*100`を実行し、400 input steps、`killed=false`、`Responding=True`、KOJOあり7,761.579ms、KOJOなし7,469.520msを確認した。これらはR39.1の速度改善値ではなく、互換性smokeの実測値である。
- compiled helper reflectionとsource auditで、Program.ErbDir外のpath除外、口上まとめを含む実フォルダのfull-reload分岐、partial loaderによるactive field上書きなし、単一`[`のeager判定、`[[`の除外を確認した。GUI環境のメニュー操作は安定しなかったため、部分再読込そのもののUI実行結果は実測PASSとして記録していない。
- follow-upでNormalはLazy対象をpromotion、DebugMode / AnalysisModeは同じ対象をnon-promotionとする条件をsource/reflection相当のfocused checkで確認した。

### 採用状態

Phase 13R39.1として正式採用した。R39のLazy設計は維持し、再読込時のmanager ownershipとpath境界だけを修正した。正式single-file配布版へ反映し、配布EXE自身でもsave219 + RepeatCount=100を実行して`400 input steps`、`killed=false`、`Responding=True`、8,369.791msを確認した。

## Phase 13R40.3 Lazy ERB設定化 + Preload bypass

### 背景

R39のLazy ERB対象は実装上固定されており、ユーザーが`Data\\setting.json`から対象フォルダや有効状態を確認・切替する正式な設定経路がなかった。また、Preload時にLazy対象の本文を先行してbulk cacheへ載せる経路が残ると、起動時に遅延させた本文が再びretainedされ、Lazy化によるmanaged/live memory削減を打ち消す可能性があった。

### 実装

- `Data\\setting.json`の日本語設定名でLazy ERBの有効状態と対象フォルダを指定できるようにした。
- 旧`LazyErb`形式は新形式へ一度だけ自動移行し、旧keyを保存後に残さない。型不整合はdefaultで隠さず設定errorとして扱う。
- 設定pathはData基準の`ERB\\`配下に限定し、絶対path、ERB root指定、不正な外部pathをLazy対象から拒否する。
- Lazy対象のPreloadでは不要なbulk cacheを作らず、通常ERB・DebugMode・AnalysisMode・reload safety・save format・GC policyは維持した。

### 効果

既存の検証済み値では、Managed memoryは約`1.311GB → 1.050GB`（約261MB、約19.9%減）、Working Setは約`2.224GB → 1.604GB`（約620MB、約27.9%減）、Peak Working Setは約`2.283GB → 1.637GB`（約646MB、約28.3%減）だった。Startup Window medianは`4176ms → 4404ms`（約227ms、約5.45%増）で、内部InitとERB parseは悪化していない。RepeatCount=1000は`58950ms → 57787ms`だった。これらは既存実測値であり、環境・fixture依存である。

実機の既存観測では、従来約2.3GB起動・継続後約3.3GB plateauだった環境に対し、R40.1 Trialは起動約1.423GB、通常継続約1.6GB付近で安定した。これはTask Managerによる参考観測であり、全ゲームで同じ削減量を保証するものではない。

### 検証

- R40.3 follow-upのfocused configuration tests、path A-J、Release buildを通過した。
- Releaseは0 errors、既存35 warnings、新規warning 0だった。
- Lazy ON/OFF、Data-relative path、旧設定migration、Preload bypass、通常のreload経路を確認済み。
- R40.1 Trialで実ゲームの起動、save219読込、口上表示、Lazy hydration、長時間プレイ時のmemory観測を実施済み。

### 採用状態

## Phase 13R41B1 Request Lazy既定対象追加

### 背景

R40.3でLazy ERBの対象を`Data\setting.json`から設定できるようになった。R41A/R41B1の実ゲーム診断では、`ERB/RPG/依頼`配下257 files / 5,137,320 bytesのうち、一覧表示に必要なfallback 81 files / 1,011,109 bytesをeagerに残し、依頼本編のLazy対象176 files / 4,126,211 bytesを初回利用まで遅延できることを確認した。save39の依頼一覧表示後も174 files / 4,116,324 bytesが未接触だったため、依頼本編を新規設定の既定Lazy対象へ加える価値があると判断した。

ただし、既存ユーザーが`setting.json`でLazy対象を明示的に限定している場合、その意図を起動時に上書きしてはいけない。今回の採用は既存配列への強制appendではなく、新規設定、Lazy設定欠落、Directories欠落/nullのdefaultだけを変更する。

### 実装

- `JSONLazyErbConfigData.Directories`の既定値を`ERB/口上/口上まとめ`と`ERB/RPG/依頼`の2件へ変更した。
- `JSONConfig.Load()`後のDirectories null補完も同じ2件へ変更し、既定値の経路を一致させた。
- Legacy migrationが作るdefaultsは`JSONLazyErbConfigData`から生成されるため、旧Directories欠落時も新defaultを使用する。
- 既存の日本語Directories配列、legacyの明示Directories、unknown property、invalid type error、Lazy loader本体、fallback判定、Preload bypass、reload、save format、GC policyは変更していない。
- 既存明示設定へ`ERB/RPG/依頼`を自動appendしない理由を`MEM-13R41B1`日本語reason commentへ記録した。

### 効果

Trialのstartup 5-run中央値では、ControlからRequest-Lazyへ次の差分を確認した。Working Setは`1,614,139,392 → 1,557,016,576 bytes`、差分`-57,122,816 bytes`（約57.1MB減）で、起動時の主要なメモリ効果とした。Managedは`-8,530,144 bytes`だがrun間ばらつきが大きいため参考値である。InputReadyは`-113.099ms`、ERB処理は`-88ms`だった。
