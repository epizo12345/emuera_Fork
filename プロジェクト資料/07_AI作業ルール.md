# Emuera.NET AI作業ルール

最終更新: 2026-08-20

この文書は、Emuera.NET / `emuera_fork` の高速化・省メモリ化・不具合修正を、ChatGPT ChatモードとCodexで継続して行うための共通作業ルールである。

会話コンテキストが切れた場合でも、この文書と現行のプロジェクト資料を読めば、同じ安全基準・検証基準・採用手順で作業を再開できることを目的とする。

## 1. 最上位原則

優先順位は次の順とする。

1. 既存ゲーム・既存セーブとの互換性
2. 正しさ・再現性・安全性
3. 実測で確認できる改善
4. 実装と保守の単純さ
5. 作業速度
6. コード量の少なさ

高速化のためにゲームの意味論を変えてはならない。

「速そう」「メモリが減りそう」という推測だけではProductionへ採用しない。実測と互換性確認を通過した変更だけを正式採用する。

## 2. ChatモードとCodexの役割分担

### 2.1 Chatモードで行うこと

Chatモードで実行可能な調査・分析・設計は、原則としてChatモード側で完了させる。

主な担当:

- ソースコードの静的調査
- GitHub上のソース・資料・履歴確認
- ログ解析
- profiler結果の解析
- ZIP / JSON / CSV / trace summaryの確認
- 原因候補の整理
- candidate案の比較
- 採用 / HOLD / REJECT判断
- 互換性リスクの整理
- 測定方法の設計
- Codexへ渡す指示文の作成
- Codex成果物のレビュー
- 資料に残すべき数値・結論の整理

Codexに「まず調査してください」と広く投げる前に、Chatモードで可能な限り対象・原因・変更案・検証方法を絞る。

### 2.2 Codexで行うこと

実環境・実repositoryへのまとまった変更が必要な作業をCodexへ渡す。

主な担当:

- 実repositoryのソース修正
- 複数ファイルにまたがる実装
- プロジェクト資料の整合更新
- Release build
- publish
- 実fixtureを使った起動試験
- formal EXEの作成
- commit
- official remoteへのpush

Chatモードで安全に直接実施できることを、Codexへ無駄に再調査させない。

### 2.3 Codex使用量

Codex使用量は実作業に優先して使う。

- 調査だけのために大量消費しない
- 既知の測定を繰り返させない
- Chat側で確定済みの事実は指示へ渡す
- 「既知の事実」と「Codex側で今回確認すべきこと」を分ける

Codexの実作業では、原則としてUI側でLunaを選択する。

ただしCodex向けの作業指示本文にはモデル名を埋め込まない。モデル選択はユーザーがUI側で行う。

## 3. Codexへ渡す指示の作り方

Codexへ実作業を依頼するときは、可能な限り一回の指示で迷わず完了できるようにする。

最低限、次を含める。

- 作業目的
- 現在のbranch
- 想定HEAD SHA
- 必要なら対象ファイルblob SHA
- 対象ファイル / 関数
- 変更してよい範囲
- 変更してはいけない範囲
- 既知の調査結果
- 既知の測定結果
- 採用する実装方針
- 互換性条件
- build条件
- test条件
- publish条件
- 資料更新対象
- commit条件
- push条件
- 停止条件
- 最終報告項目

「周辺も適当に改善しておいて」のような曖昧な依頼は避ける。

想定外の状態に遭遇した場合は、無関係な修正へ広げず停止して報告させる。

## 4. Ponytailの考え方を参考にする

参考:

https://github.com/DietrichGebert/ponytail

このプロジェクトでは、Ponytailの考え方のうち特に次を採用する。

1. まず本当に変更が必要か確認する
2. repository内の既存実装を再利用する
3. .NET / C#標準機能を優先する
4. 既に導入済みの依存関係を優先する
5. 同じ効果なら影響範囲の小さい修正を優先する
6. validation / error handling / data loss対策 / 互換性guard / bounds / overflow / cleanupは削らない
7. コードを短くすること自体を目的にしない

変更不要なら変更しない。

## 5. 互換性は性能より上位

Productionへ採用する変更は、原則として次を維持する。

- 既存セーブを変換なしで読み込める
- 新規ゲーム開始を要求しない
- セーブ形式を変えない
- ERB / ERH / CSVの意味を変えない
- ERB評価順を変えない
- 関数呼出回数を変えない
- 副作用式の評価回数を変えない
- RNG消費順を変えない
- 入力順を変えない
- `WAIT` / `TWAIT` の意味を変えない
- 入力待ちの意味を変えない
- 右クリック / ESC / スキップの意味を変えない
- マクロ中断の意味を変えない
- 最終ゲーム状態を変えない
- nested / recursive callの独立性を壊さない
- 例外時に共有状態を壊さない

性能改善と互換性が衝突する場合は、互換性を優先する。

## 6. 1フェーズ1目的を基本にする

原則として、1つのPhaseには1つの主要目的だけを持たせる。

例:

- startup allocation
- retained memory
- runtime allocation
- HTML allocation
- macro speed
- bugfix
- Gamepad

無関係な変更を同じPhaseへ混ぜない。特に、性能改善とGamepad対応など独立した作業は分離する。

## 7. 調査 → candidate → 検証 → 正式採用

性能改善は次の段階を基本とする。

### 7.1 調査

- hot path / allocation sourceを特定
- 実ゲームfixtureで頻度を確認
- 変更可能範囲を確認
- 互換性リスクを確認

### 7.2 candidate

Production sourceを不用意に変更せず、可能ならisolated candidateとして実装する。

### 7.3 検証

- build
- focused test
- shadow differential
- same-input differential
- startup smoke
- runtime smoke
- 実ゲーム確認

など、変更内容に合う方法で確認する。

### 7.4 正式採用

十分な証拠が揃ってからProductionへ反映する。

診断と正式採用を同じ作業として扱わない。

## 8. 診断コードとProductionコードを分離する

次は原則として診断用だけにする。

- profiler hook
- shadow execution
- allocation measurement
- debug log
- temporary counters
- candidate-only branch
- diagnostic DLL
- trace collection code
- `PERFORMANCE_METRICS`を前提にした診断処理

正式配布版では不要な診断処理を残さない。

Production publishでは原則 `EnablePerformanceMetrics=false` とする。

## 9. 作業開始時にbaselineを固定する

重要な作業を開始する前に、最低限次を確認する。

```text
branch
HEAD SHA
git status
index state
remote
```

必要に応じて次も固定する。

```text
対象source blob SHA
正式EXE size
正式EXE SHA-256
fixture
save
.NET SDK version
```

想定HEADや対象sourceが違う場合、「似ているから大丈夫」と推測してpatchしない。

前提不一致なら停止して報告する。

## 10. 検証済みcandidateを再発明しない

既にbuild / smoke / differentialを通したcandidateがある場合、正式採用時に説明文から似たコードを再実装しない。

正本として優先するもの:

1. 実際に検証したsource
2. 実際に検証したdiff
3. 実際に検証したcommit
4. それらを固定したSHA

正式採用で許容する変更は、production用コメントへの整理など意味論を変えない範囲とする。

次を勝手に変更しない。

- predicate
- fallback条件
- null処理
- overflow処理
- 型
- 評価順
- allocation lifetime
- helper使用方法
- recursive / nested behavior

## 11. 性能改善は実測する

「速そう」という理由だけでProductionへ採用しない。

目的に応じて測定対象を分ける。

### allocation削減

- allocated bytes
- allocation rate
- allocation type
- allocation stack / site

### retained memory削減

- managed memory
- Working Set
- Private Bytes
- object count / retained graph

### CPU高速化

- wall time
- CPU time
- hot stack
- operation count

### startup高速化

- process startからInputReadyまで
- startup allocation
- startup GC
- multiple-run中央値

## 12. 同条件比較を優先する

A/B比較ではworkload差を最小化する。

優先順位:

1. same-input differential
2. exact fixture / exact script
3. repeated benchmark
4. manual gameplay A/B

manual gameplay A/Bは、プレイ内容が違えば総allocationや総時間の直接比較に使わない。

warmup、startup contamination、order bias、cache effectsを考慮する。

単発値だけで大きな結論を出さない。

## 13. 数値の適用範囲を誇張しない

例:

「FONT fast path対象経路でallocation約80.8%削減」

を、

「ゲーム全体のメモリが80.8%減る」

と書いてはならない。

必ず区別する。

- 対象type限定
- 対象site限定
- 対象path限定
- fixture限定
- measured window限定
- ゲーム全体

また次を混同しない。

- allocation
- retained memory
- managed heap
- Working Set
- Private Bytes
- GC high-water mark

## 14. HOLD / REJECTも成果として記録する

改善しなかったcandidateを無理に採用しない。

次のような場合はHOLD / REJECTにする。

- 効果が測定誤差程度
- 明確に遅くなった
- allocationは減るがCPUが大きく悪化
- coverageが極端に低い
- 互換性リスクが高い
- 複雑性に対して利益が小さい
- workload差で効果を証明できない

不採用理由は資料へ残す。

同じ案を理由を忘れて何度も再試行しない。

ただし、前提やruntimeが変わった場合は再検討してよい。

## 15. 正式採用前に最終diffを確認する

Productionへ入れる直前に必ず確認する。

```powershell
git diff --check
git status --short
git diff --stat
git diff
```

確認項目:

- candidateとProductionの意味論が一致している
- 診断コードが混入していない
- 無関係なファイルを変更していない
- Gamepadなど別Phaseの変更が混ざっていない
- 一時artifactがtrackedになっていない
- 資料の数値が実測と一致している
- 配布EXEのhashが一致している

## 16. 正式publish条件

Emuera.NETの正式配布版は原則として次の条件を使用する。

```text
Configuration: Release
Runtime: win-x64
framework-dependent
self-contained: false
PublishSingleFile: true
EnablePerformanceMetrics: false
```

例:

```powershell
dotnet publish .\Emuera.csproj `
  -c Release `
  -r win-x64 `
  --self-contained false `
  -p:PublishSingleFile=true `
  -p:EnablePerformanceMetrics=false `
  -o <publish dir>
```

正式配布物はsingle-file `Emuera.exe`。

数百KB程度の通常apphostを正式配布EXEと誤認しない。

publish後は次を確認する。

- `Emuera.exe`が存在
- おおむね従来同様のsingle-fileサイズ
- `Emuera.dll`を正式配布物として横に置いていない
- SHA-256を算出
- 実際のpublish設定がformal条件と一致

## 17. 正式EXEそのものをsmokeする

`dotnet build`成功だけでは正式採用完了としない。

正式に配布へ置くEXEそのものを実ゲームfixtureで起動する。

変更内容に応じて確認する。

- 起動
- InputReady
- 既存セーブ読込
- 通常進行
- 対象機能
- 入力
- WAIT
- 表示
- 文字色
- 改行 / wrap
- 選択肢
- HTML
- マクロ
- 中断
- 例外

process exit code 0だけを「画面表示・ゲーム挙動まで完全PASS」と表現しない。

GUI目視が必要ならユーザー確認を求める。

## 18. 正式push時は配布EXEと資料を同期する

Production sourceを正式採用してpushする場合、可能な限り同じcommit / push内で配布版と現行資料も更新する。

最低限確認する。

### 配布

- `配布/Emuera.NET_最終通常版/Emuera.exe`
- `配布/Emuera.NET_最終通常版/README.md`
- `配布/Emuera.NET_最終通常版/SHA256SUMS.txt`

### プロジェクト資料

- `プロジェクト資料/01_仕様書.md`
- `プロジェクト資料/02_引き継ぎ書.md`
- `プロジェクト資料/03_資産目録.md`
- `プロジェクト資料/04_編集ルール.md`
- `プロジェクト資料/05_採用済み変更ファイル一覧.md`
- `プロジェクト資料/06_コード案内.md`
- 日付付きの今回の修正説明
- `更新履歴.md`
- repository root README等、今回の変更で古くなる現行説明

ただし変更の影響を受けない資料を無理に書き換えない。

repository全体を検索して、旧EXE size / SHAや「次候補」など、正式採用後に古くなる現行記述が残っていないか確認する。

## 19. 作業履歴は判断過程まで書く

説明資料には「何を変更した」だけでなく、後から別のChat / Codexが読んで判断を再現できる情報を残す。

最低限書く。

### 背景
- なぜ調査したか
- 何が問題だったか
- 実ゲームでどう見えていたか

### 調査
- 何を測ったか
- どこがhotだったか
- どの候補を比較したか

### 実装
- 何を変更したか
- なぜその方式を選んだか
- なぜ別案を選ばなかったか

### 互換性
- 評価順
- RNG
- input
- save
- recursion
- fallback
- exception

などをどう守ったか。

### 検証
- fixture
- duration
- calls
- bytes
- time
- mismatch
- exception
- build errors / warnings
- smoke

### 結果
- どれだけ改善したか
- 何には効かないか
- 数値の適用範囲

### 次
- 次に見るべき候補
- HOLDしたもの
- 再検討条件

作業履歴はChatモードのコンテキスト切れ対策でもある。

## 20. 現行資料とhistorical記録を区別する

次のような現行資料は常に最新状態へ合わせる。

- 仕様書
- 引き継ぎ書
- 資産目録
- コード案内
- 配布README

一方、過去の日付付き調査記録は、当時の記録として正しければ後から改変しない。

ただし「今回の修正説明」の末尾にある「次候補」が今回正式採用された場合など、現行状態を誤認させる記述は適切に更新する。

## 21. 一時artifactは恒久資産ではない

次は原則として一時物。

- `.nettrace`
- `.etlx`
- `.gcdump`
- diagnostic DLL
- scratch source
- temporary publish
- temporary ZIP
- profiler raw output
- screenshots
- repeated raw logs
- `artifacts/`以下の作業物

採用判断が終わったら削除してよい。

恒久的に残すものは原則:

- 採用済みsource
- formal EXE
- SHA
- 重要な測定要約
- 採用 / 不採用理由
- 再現に必要な最小情報

数GBのartifactをrepository周辺へ残し続けない。

## 22. ユーザーへ渡すscriptは事前監査する

Chat側でscript / ZIPを作成した場合、ユーザーへ渡す前に可能な限り確認する。

### Python
- `py_compile`
- import
- path
- argument
- exception handling

### PowerShell
- quoting
- line continuation
- parameter passing
- PowerShell version
- external command invocation

### 共通
- expected HEAD
- blob pin
- source anchor
- repositoryを直接壊さないか
- rollback可能か
- output path
- build command
- publish command
- cleanup
- ZIP CRC
- SHA-256

Windows実環境でしか確認できない部分は明示し、可能なら `--check-only` / `--build-only` を用意する。

事前に静的に発見できるscriptミスを、ユーザーの実行で初めて発見する状態をできるだけ避ける。

## 23. rollbackを考えてから変更する

Production変更では、失敗したときに元へ戻せる状態を確保する。

- clean working treeから開始
- baseline HEADを固定
- isolated candidateを優先
- 未commit変更を混ぜない
- 必要ならbackup
- failed apply時のrestore
- formal commit前のdiff確認

不明な状態で`reset --hard`やforce pushを自動実行しない。

## 24. Git運用

### 24.1 正式系

正本は原則:

```text
local main
GitGud origin/main
```

GitGudへの正式push後、GitHub mirrorも同期する。

### 24.2 GitHub mirror

GitHub側はPR merge commitによりGitGud / local mainとSHA系列が異なる場合がある。

その場合は直接force pushしない。

基本:

```powershell
git push github main:<temporary-branch>
```

GitHub上で:

```text
temporary branch
↓
Pull Request
↓
mainへMerge
↓
temporary branch削除
```

`git push github main --force`は原則禁止。

### 24.3 診断フェーズ

診断だけのPhaseでは、明示的な必要がない限りcommit / pushしない。

### 24.4 正式採用

正式採用では、実装・配布・資料・hash更新を可能な限り同じcommitへまとめる。

## 25. commit前の禁止事項

次を正式commitへ混ぜない。

- raw trace
- profiler cache
- temporary candidate DLL
- scratch project
- large artifact
- unrelated Gamepad work
- unrelated cleanup
- unrelated warning fix
- test fixture本体
- private save
- diagnostic-only logs

## 26. Codexの停止条件

次の場合、Codexは推測で続行せず停止して報告する。

- 想定branchではない
- 想定HEADではない
- tracked working treeが予期せずdirty
- authoritative candidate / diffが見つからない
- source anchorが一致しない
- build error
- formal publish条件を満たせない
- formal EXE smokeで異常
- 既存セーブ互換性に疑義
- unrelated changeが混入
- 測定結果が採用条件を満たさない
- 必要な検証資産が存在しない

停止は失敗ではない。推測実装をProductionへ入れるより正しい。

## 27. Codexの最終報告

正式作業完了時は最低限次を報告する。

- branch
- base HEAD
- final commit SHA
- commit message
- push結果
- 変更ファイル一覧
- Release build errors
- Release build warnings
- formal EXE size
- formal EXE SHA-256
- smoke結果
- 更新した資料一覧
- 実装の要約
- 測定値の要約
- HOLD / REJECTした内容
- GitHub mirrorを更新したか
- 未解決事項

## 28. 性能改善の最終判断

次の条件を満たす変更を優先する。

```text
効果が実測できる
+
互換性が保たれる
+
実装が小さい
+
fallbackが明確
+
保守しやすい
```

逆に、

```text
効果が小さい
+
複雑性が増える
+
互換性リスクが高い
```

なら、実装できても採用しない。

最終目標は「コードを増やすこと」ではなく、

**既存ゲームを壊さず、Emuera.NETを実ゲーム上で軽く・速く・安定して動かすこと**

である。

## 29. 新しいChat / Codexでの再開手順

新しい会話や新しいCodex sessionで作業を再開するときは、まず次を読む。

1. `プロジェクト資料/07_AI作業ルール.md`
2. `プロジェクト資料/02_引き継ぎ書.md`
3. 最新の `プロジェクト資料/修正履歴/#今回の修正説明_*.md`
4. `更新履歴.md`
5. 作業対象に応じて `01_仕様書.md` / `06_コード案内.md`

その後、

```powershell
git branch --show-current
git rev-parse HEAD
git status --short
git remote -v
```

を確認し、現行baselineを固定してから新しいPhaseを開始する。
